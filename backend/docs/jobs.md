# Сохраняемые задания проверки

`POST /v1/normalize` сохраняет прежнее синхронное поведение, ничего не записывает в журнал заданий и не использует его для поиска ответов. Для работы оператора добавлен отдельный ресурс.

| Метод | Назначение |
| --- | --- |
| `POST /v1/normalization-jobs` | Массив или `{records:[...]}`; сначала сохраняет вход, возвращает `202` и задание |
| `GET /v1/normalization-jobs` | Список кратких описаний, новые сначала |
| `GET /v1/normalization-jobs/{job_id}` | Входные записи, результаты, статус, ревизия, признаки проверки |
| `POST /v1/normalization-jobs/{job_id}/records/{record_index}/review` | Сохранение полей одной записи с `expected_revision` |
| `GET /v1/normalization-jobs/{job_id}/records/{record_index}/candidates` | Совместимые населённые пункты, ревизия задания и версия справочника |
| `POST /v1/normalization-jobs/{job_id}/records/{record_index}/selections` | Выбор сущности и пересчёт одной записи |
| `DELETE /v1/normalization-jobs/{job_id}` | Удаление завершённого или неуспешного задания, `204` |

Лимиты входа совпадают с normalize: 1–1000 записей, строка до 4096 байт, тело до 2 MiB, ID — строка или int64. Создание принимает массив или объект `{records:[...]}` и возвращает один формат ресурса задания. `record_index` — исходная позиция с нуля: дубликаты пользовательского ID не объединяются. Raw и тип ID сохраняются; JavaScript-клиентам большие ID нужно передавать строками.

Один фоновый worker последовательно обрабатывает задания: `queued` → `running` → `completed` / `failed`. Браузер опрашивает активное задание раз в секунду, закрытие страницы не отменяет обработку. Промежуточных результатов и численного прогресса внутри пакета пока нет. После рестарта `running` возвращается в очередь и весь пакет обрабатывается заново; завершённые задания и правки не пересчитываются. При перезапуске используется текущая конфигурация моделей/справочников; закрепление их snapshot для незавершённых заданий ещё не реализовано.

## Правки

Тело review: `{expected_revision, fields}`. `fields` содержит ту же структуру `AddressFields`, включая детали доставки; координаты для этого действия не требуются. Успех возвращает обновлённое задание. Сохранение другой строки не пересчитывает и не перезаписывает предыдущие правки. Операция отмечает `reviewed[index]=true`, увеличивает ревизию; автоматическая уверенность не повышается. Признак проверки оператором не означает подтверждённую геопозицию.

При изменении любого поля здания прежние coordinates/catalog_id/catalog_revision сбрасываются, статус становится `needs_review`. Исходные диагностические предупреждения сохраняются вместе с отметкой ручной проверки; они описывают автоматический разбор, а не повторное согласование исправленного адреса.

Подтверждение здания остаётся отдельным каталоговым действием. Review может дополнительно передать `confirmed_catalog_id`: сервер принимает только подтверждённое здание с полностью совпадающими полями здания и берёт координаты из каталога. Доставочные поля не сохраняются в каталоге. Два HTTP-действия не являются общей транзакцией: если подтверждение прошло, а review завершился ошибкой, UI сообщает о частичном сохранении.

Устаревшая revision возвращает `409 job_revision_conflict`, завершённость задания также проверяется. UI сохраняет черновик при ошибке и предлагает явно загрузить сохранённую версию. Повтор сохранения с уже использованной ревизией получает конфликт; после потерянного ответа нужно перечитать задание. Неизвестный/истёкший job или индекс — `404`, переполнение хранилища — `507`.

## Выбор населённого пункта

После завершения задания UI запрашивает кандидатов только для открытой записи. Ответ candidates: `{revision, reference_version, candidates:[{entity_id, name, settlement_type, province, province_id, source}]}`. Варианты основаны на исходной строке и локальном справочнике. Явно указанная область ограничивает список; конфликт нескольких областей или разных населённых пунктов не разрешается произвольным выбором. Тип берётся только из явных квалификаторов источника (`г.`, `с.` и т. п.); при отсутствии или конфликте — null. Нет ранжирования по популярности. Даже при одном автоматически уточнённом варианте UI может показать одноимённые сущности для проверки; отсутствие дома в неполном OSM не исключает населённый пункт.

Тело selections: `{expected_revision, reference_version, entity_id}`. Версия — SHA-256 полного файла текущего immutable SQLite, включая адресные факты и алиасы. При её изменении сервер возвращает `409 reference_version_conflict`; надо перечитать кандидатов. При изменении задания — `409 job_revision_conflict`; надо загрузить сохранённую версию. Несовместимая сущность — `400 invalid_selection`.

Сервер снова разбирает точную исходную строку с выбранным ID как ограничением: восстанавливает область, заново согласует улицу, тип, район и confidence; legacy-поля координат и каталога остаются `null`. Не дописывает город или область в raw. Старые ручные исправления **этой записи заменяются пересчётом**, другие записи остаются нетронутыми; интерфейс предупреждает об этом перед действием и блокирует выбор при несохранённом черновике. Неизвестные зависимости остаются null. Building overlay при этом не читается.

Последующая ручная правка города или области снимает прежний выбор сущности, чтобы интерфейс не показывал несовместимый отмеченный вариант. Выбор сохраняется в `city_selections` с позицией записи, ID сущности, версией и ревизией применения. Успех возвращает обновлённое задание. `reviewed[index]` сбрасывается: выбор административной сущности не означает проверки всего адреса. Повтор последнего выбора с той же или непосредственно предшествующей ожидаемой ревизией возвращает сохранённый результат без нового изменения ревизии; после других правок такой retry уже конфликтует. Выбор не вызывает catalog confirmations и не повышает confidence до 100%. Автоматическая оценка пересчитывается по обычным признакам. Старый синхронный normalize сохраняет поведение и форматы.

## Хранение

Путь задаёт `JOBS_PATH`. По умолчанию `normalization-jobs.json` рядом с `CATALOG_OVERLAY_PATH`: локально `var/`, в Docker `/data/` в существующем постоянном томе. Это отдельный приватный журнал работы, не building overlay и не кеш нормализации.

Ограничения первого варианта: до 50 заданий, до 64 MiB сериализованного журнала, хранение 7 дней с последнего изменения задания. Чтение не продлевает срок. Worker удаляет истёкшие записи с диска при очередном проходе (примерно раз в секунду); при остановленном сервисе очистка произойдёт на следующем запуске. Завершённые задания можно удалить через интерфейс. При слишком большом результате задание получает `failed` вместо бесконечного ожидания сохранения.

Один процесс владеет одним журналом. Mutex защищает изменения, запись использует временный файл с правами 0600, fsync и атомарный rename; память меняется после успешной записи. Директория не fsync-ится: внезапная потеря питания не входит в гарантию, как и для каталога. Повреждённый журнал останавливает запуск. Резервное копирование/восстановление выполняется при остановленном процессе; файл содержит приватные адреса и детали доставки, исключён из Git вместе с `var/`. Удаление Docker-тома удаляет задания.

API не имеет встроенной авторизации. Используйте локальный экземпляр или существующий защищённый шлюз; CORS не разделяет операторов и задания по пользователям. Ответы job API имеют `Cache-Control: no-store`. В браузерное хранилище адреса не записываются, URL содержит только случайный job ID.

Явные ориентиры (`магазин`, `школа`, `аптека`) исключаются из справочного поиска административных сущностей и не могут сами породить город. Их названия сохраняются в `landmark`; такое же название, отдельно написанное как населённый пункт, остаётся допустимым. При отсутствии совместимых кандидатов интерфейс предлагает уточнить город/область вручную или создать новый пакет с уточнённой строкой. Сохранённые задания содержат прежние результаты и не переписываются автоматически при обновлении алгоритма.
