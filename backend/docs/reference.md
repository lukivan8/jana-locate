# Справочник КАТО и OSM

Публичный снимок содержит 66 339 сущностей: 15 586 записей официального КАТО от 18 сентября 2026 года, 47 663 логические улицы OSM и 3090 жилых территорий. Отдельный сжатый файл содержит 1 078 711 структурных адресных свидетельств OSM (населённый пункт, улица/территория, номер дома, ID источника), без координат.

КАТО покрывает Казахстан. OSM подготовлен из extract всего Казахстана; timestamp базы `2026-10-15T20:21:00Z` (16 октября по Алматы). Улицы доступны для 1133 населённых пунктов: в том числе 1849 в Астане, 804 в Караганде, 4369 в Алматы и 3213 в Шымкенте. Это количество логических объектов после объединения сегментов, не обещание полной адресной базы этих городов.

Привязка выполняется по административным/поселенческим полигонам OSM, aliases КАТО и явным `addr:city`. Неоднозначные или отсутствующие связи пропускаются: в manifest отдельно указаны 194 097 таких объектов и шесть некорректных границ. Шесть непригодных номеров домов исключены. Покрытие остаётся частичным; отсутствие адреса в справочнике не доказывает его несуществование.

## Сборка

Из корня Go-репозитория:

```sh
python3 tools/build_reference.py \
  --input data/reference/entities.jsonl \
  --manifest data/reference/manifest.json \
  --output data/reference/reference.sqlite
```

Команда работает без сети, используя включённые `entities.jsonl`, `addresses.jsonl.gz`, `districts.jsonl.gz` и manifest. Сжатые адреса читаются потоково, без внешних библиотек. SQLite исключена из Git и собирается также внутри Dockerfile. Конструктор проверяет контрольные суммы, количество записей, типы, повторяющиеся ID, ссылки, принадлежность улицы/адреса одному населённому пункту и целостность SQLite, атомарно заменяет файл и делает его read-only. При ошибке прежняя SQLite сохраняется.

Задайте `REFERENCE_PATH` при запуске. Go открывает SQLite с `mode=ro&immutable=1`, загружает индекс псевдонимов в память и закрывает SQL-соединение. Для обновления снимка пересоберите файл и перезапустите процесс; не меняйте файл в процессе его загрузки.

## Схема версии 3

- `metadata(key,value)` — версия и manifest источников.
- `entities(id,kind,name,parent_id,city_id,province_id,district_id,street_type,source)` — административные и уличные сущности.
- `aliases(entity_id,alias)` — доступные названия, варианты языка и исторические имена.
- `addresses(id,street_id,city_id,house,source)` — положительное свидетельство адреса. Номер сохраняется строкой, включая дроби и литеры; диапазоны не интерполируются.

- `district_objects(object_kind,object_id,city_id,complete,source)` — полнота покрытия геометрии адреса или улицы.
- `district_links(object_kind,object_id,district_id)` — все совместимые районные идентичности, без выбора единственного кандидата.

Читатель поддерживает snapshots версий 1 (без адресов) и 2 (без районных отношений). Старые readers не читают схему 3: сервис и данные обновляются вместе. Внешний HTTP-контракт не меняется.

Справочник не содержит координат зданий. Он не заменяет seed или overlay и не принимает записи подтверждений. Геометрия используется только на этапе подготовки. Родительские связи КАТО выводятся из иерархии кодов; сегменты OSM объединяются по логической улице в конкретном населённом пункте. Адресные названия без типа объединяются с единственным совместимым типизированным объектом этого населённого пункта; конфликтующие типы не склеиваются.

При нескольких одноимённых населённых пунктах нормализатор может уточнить уже упомянутый город по точному сочетанию улицы и дома. Например, `Караганда, Алалыкина 12` теперь определяет Карагандинскую область и тип `улица`. Одинокое название улицы не назначает город. Неизвестный дом или положительные адресные свидетельства сразу для двух кандидатов сохраняют неоднозначность. Район дополняется только при отдельном положительном свидетельстве районного покрытия или иерархии КАТО. Координаты не создаются.

## Обновление источников

[`manifest.json`](../data/reference/manifest.json) содержит URL, время снимка, SHA-256 исходников и JSONL, покрытие и атрибуцию. Обновление — явная подготовительная операция вне runtime. Инструменты загрузки и преобразования доступны в [jana-locate/scripts/reference](https://github.com/lukivan8/jana-locate/tree/main/scripts/reference). При переносе нового JSONL переносите соответствующий manifest и проверяйте иерархии, переименования, омонимы и границы покрытия.

Из корня полного репозитория:

```sh
uv venv .artifacts/reference-venv
uv pip install --python .artifacts/reference-venv/bin/python -r scripts/reference/requirements.txt
make reference-fetch      # явная онлайн-подготовка КАТО и Geofabrik PBF; существующие файлы переиспользуются
make reference-prepare    # офлайн-преобразование локальных исходников
make reference-test
make reference            # сборка SQLite без зависимостей подготовки и без сети
```

Для обновления уже скачанных исходников: `.artifacts/reference-venv/bin/python scripts/reference/fetch.py --refresh`. Legacy `--osm-source astana` оставлен для подготовки старого ограниченного снимка; основной путь теперь использует Казахстан.

Самостоятельный backend может повторить OSM-импорт через `tools/import_osm.py --base data/reference/entities.jsonl --pbf LOCAL.osm.pbf --output NEW/entities.jsonl --addresses NEW/addresses.jsonl.gz --manifest NEW/manifest.json`, установив только подготовительные зависимости osmium 4.3.0 и shapely 2.1.2. Этот путь сохраняет КАТО из base; для обновления самого КАТО используется подготовка workbook в полном репозитории. Подготовительные Python-зависимости не нужны сервису Go: он читает уже подготовленный SQLite.

В текущем importer геометрии адресных nodes/ways используются для контекста; адреса, заданные только relations, не импортируются. Районные отношения улиц/домов назначаются по полной наблюдаемой геометрии на этапе подготовки, с сохранением многозначности и неполноты. OSM остаётся источником свидетельств, а не ручным подтверждением каждого здания.

Реализация подготовки районных отношений, работы с улицами через несколько районов
и неоднозначностью описан в [district-reference-plan.md](district-reference-plan.md).
Он также учитывает районы Астаны и Тұран, которые в текущем КАТО-снимке имеют
исходный тип `admin`; классификация только по `kind=district` недостаточна.
