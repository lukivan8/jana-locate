# Jana CLI

Самостоятельный локальный потребитель API нормализации. CLI читает колонку PostgreSQL, сохраняет согласованный снимок и прогресс в SQLite, вызывает `/v1/normalize` порциями по 100 записей и поднимает встроенный сайт для проверки. После явной команды записывает отдельную связанную таблицу в PostgreSQL. Доступ к исходной базе есть только у CLI; сервис нормализации получает адреса и временные позиционные ID.

`cli/` собирается отдельно. Нет импортов backend, Go workspace, Node в runtime или сборки сайта при запуске. Go-бинарник и контейнер содержат ту же SPA из `frontend/`, включая общий wizard, очередь и редактор. В локальном режиме страница работает с API CLI: журнал SQLite, снимки PostgreSQL, постраничная проверка и явная публикация. Пароль БД и API-токен браузеру не передаются. Отдельного исходного интерфейса CLI нет.

## Готовые контейнеры — основной способ установки

```sh
# Полностью автономный локальный комплект
curl -fsSL https://raw.githubusercontent.com/lukivan8/jana-locate/main/scripts/install.sh | sh -s -- full
cd jana-locate
./jana connect
./jana normalize
```

Модели и справочники уже входят в API-образ; Go, Node.js, Python и сборка исходников не нужны. После скачивания комплект работает без внешней сети. PostgreSQL пользователь подключает отдельно.

Для использования hosted API вместо локального нормализатора:

```sh
curl -fsSL https://raw.githubusercontent.com/lukivan8/jana-locate/main/scripts/install.sh | sh -s -- hosted
```

Этот режим скачивает только CLI со встроенным сайтом и отправляет адреса на `https://jana.linker.kz`. Пароль PostgreSQL остаётся у локального CLI. Сайт — `http://localhost:8095`, открывается без логина и пароля. [Полная инструкция](../docs/quickstart.md).

В готовом комплекте используйте `./jana`, в исходном репозитории для разработки — `./cli/jana`. Следующие команды со сборкой относятся к разработческому стенду.

## Сборка API, сайта и CLI из исходников — для разработки

Из корня репозитория:

```sh
./cli/jana up
```

Команда собирает и запускает **два** контейнера: API нормализации и CLI со встроенным сайтом. PostgreSQL не запускается; подключение к своей базе настраивается отдельно. Режим сети выбирается автоматически для обычного Linux Engine и Docker Desktop; привязки к сетям или именам контейнеров конкретной базы нет.

- Сайт: `http://localhost:8095/`, без логина и пароля.
- API: `http://localhost:8080/` (проверка готовности: `/readyz`).
- CLI: `./cli/jana connect`, затем `./cli/jana normalize` (публикация по `a`).

`connect` предлагает мастер; после сохранения профиля достаточно `normalize`. W выводит ссылку на сайт для открытия на хосте. Docker-контейнеры остаются работать после завершения CLI. Профиль, задания и исправления сохраняются в отдельном томе этого стенда. Для флагов: `./cli/jana normalize --help`; для просмотра запусков: `./cli/jana runs`.

Переменные окружения `CLI_PORT`, `CLI_API_PORT` меняют порты, например `CLI_PORT=8096 CLI_API_PORT=8081 ./cli/jana up`. Для следующих команд используйте те же переменные; при запуске `up` сайт открывается с соответствующим внешним портом. `JANA_LOCAL_PROJECT` позволяет держать отдельные стенды. API и веб доступны только через localhost. Вводимые пути к файлам относятся к контейнеру; данные CLI находятся в `/data`.

Остановка без удаления данных: `./cli/jana down`. Статус: `./cli/jana status`. Логи: `./cli/jana logs`. Дополнительные Compose-команды: `./cli/jana compose restart workspace`. Первый build может занять время: модели libpostal подготавливаются при сборке; во время работы скачиваний нет. Стенд использует готовый libpostal и справочник; `MODELS_REQUIRED=false` явно допускает запуск без дополнительных моделей.

### Подключение к своей базе

`connect` принимает обычные host/port/database/user/password/table/column через мастер или флаги. Настройки конкретной БД не включены в Compose; существующая база не запускается и не изменяется при старте приложения.

На **Linux с обычным Docker Engine** launcher автоматически добавляет `compose.host.yaml`: только CLI использует сеть хоста. В мастере можно указать `localhost` и обычный порт своей PostgreSQL, включая порт другой БД, опубликованный на `127.0.0.1`. API остаётся отдельным контейнером. Веб слушает только `127.0.0.1`, как и опубликованный API. Docker Compose должен поддерживать `!reset` (v2.24.4+).

На **Docker Desktop** используется обычный bridge-режим: для PostgreSQL на компьютере укажите `host.docker.internal` и её порт; для удалённой базы — её обычный DNS/IP. База и firewall должны разрешать соединение из Docker. Можно явно выбрать `JANA_NETWORK_MODE=host` (на Desktop предварительно включите поддержку host networking) или `JANA_NETWORK_MODE=bridge`. См. [Docker host networking](https://docs.docker.com/engine/network/drivers/host/) и [подключение к сервисам хоста на Desktop](https://docs.docker.com/desktop/features/networking/networking-how-tos/).

Для прямого запуска Compose на Linux:

```sh
docker compose -p jana-cli-local -f cli/compose.local.yaml -f cli/compose.host.yaml up --build -d --wait
```

На Desktop достаточно `compose.local.yaml`. Дальше `./cli/jana connect` выбирает соответствующий режим автоматически; настройки для конкретной базы сохраняются только в локальном профиле после проверки. Launcher рассчитан на локальный Docker daemon; при работе с удалённым Docker хост относится к машине daemon.

Этот launcher рассчитан на API из данного репозитория. Для отдельного CLI с внешним API используйте обычный `compose.yaml`, описанный ниже. Сборка CLI остаётся независимой от backend; его каталог нужен только при сборке соседнего API для локального стенда.

## Локальный запуск

Для сборки нужен Go 1.23+. Локальный бинарник проверен на Linux; контейнер включает весь runtime:

```sh
go build -o bin/jana ./cmd/jana
```

Настройте PostgreSQL в своём окружении: `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGPASSFILE`/`.pgpass`, либо `JANA_DATABASE_URL`. Драйвер pgx принимает стандартные переменные и параметры подключения; URI и пароли не нужны в браузере. Для секретов из файлов поддерживаются `JANA_DATABASE_URL_FILE`, `JANA_API_TOKEN_FILE` и `JANA_WEB_TOKEN_FILE`. [Документация pgx](https://pkg.go.dev/github.com/jackc/pgx/v5@v5.7.2).

## connect → normalize

```sh
./bin/jana connect
./bin/jana normalize # a — публикация готовых записей
```

`connect` последовательно спрашивает хост, порт, базу, пользователя, пароль, SSL mode, затем после проверки соединения предлагает выбрать таблицу и колонку стрелками ↑/↓ с подтверждением Enter, определяет PK и спрашивает таблицу результата. Enter сохраняет предлагаемое значение; пароль в обычном терминале вводится без эха. Проверяет подключение, типы и права, затем атомарно сохраняет локальный профиль `var/connection.json` с правами `0600`. Профиль содержит пароль, если он был указан. Путь задаётся через `--profile`; журнал — через `--state`. Оба пути должны совпадать у следующих команд.

Полностью без интерактивного ввода (пароль задайте через `PGPASSWORD`, `.pgpass` или `JANA_DATABASE_URL_FILE`):

```sh
./bin/jana connect --host localhost --port 5432 --database app --user operator \
  --sslmode require --schema public --table orders --key id --column address \
  --target-schema public --target-table orders_jana_addresses \
  --api-url http://localhost:8080 --no-interactive
```

Также доступны `--database-url`, `--password` и `--password-stdin` (одна строка stdin). Секреты удобнее передавать окружением/файлом, чтобы не помещать их в историю команд. Сохранённый профиль используется следующими командами; `--database-url` явно переопределяет его. При изменении источника выполните `connect` заново. Нормализатор никогда не получает эти параметры.

`normalize` при отсутствии профиля запускает мастер подключения, затем сохраняет снимок и обрабатывает адреса порциями по 100. Единый экран остаётся открытым во время разбора, проверки и публикации. В нём доступны прогресс, поиск, фильтр, сортировка, страницы, детали и причины проверки. **c** предлагает подтвердить выбранный результат после просмотра полного адреса; **e** открывает текстовую форму в терминале, **w** — веб-редактор. **a** показывает состав публикации, **y** записывает готовые записи. После частичной записи экран показывает оставшиеся неподтверждённые адреса. **q** сохраняет журнал и выходит; уже выполненная публикация сохраняется. Сайт работает, пока открыта команда. Для постоянного сайта используйте отдельный `serve` с тем же журналом — CLI переиспользует его worker и web URL.

Каждая успешная порция и каждое сохранённое исправление фиксируются в SQLite. После остановки продолжить конкретный запуск можно так:

```sh
./bin/jana normalize --run RUN_ID
./bin/jana normalize --run RUN_ID --no-interactive --quiet
```

`--no-interactive` отключает терминальный интерфейс и завершает команду после обработки; `--quiet` оставляет итоговый JSON в stdout. Обычный `normalize` продолжает последний незавершённый журнал того же сохранённого подключения, источника, API и таблицы результата. `--new` создаёт новый снимок. Файловый ввод через `--file` создаёт новый запуск; для продолжения укажите `--run`. URL API закреплён в запуске; версии моделей одного endpoint пока не закрепляются. По умолчанию сайт слушает `127.0.0.1:8095`, API — `http://localhost:8080`.

Для автоматизации `normalize --run RUN_ID --confirm --quiet` явно публикует готовые записи после обработки. Без `--confirm` построчный и неинтерактивный режимы завершаются после обработки и сохраняют журнал. `--plain` отключает полноэкранный интерфейс. Совместимые команды `publish` и `land` сохранены для существующих скриптов; основной сценарий полностью находится в `normalize`.

Для PostgreSQL создаётся отдельная таблица с `source_id` исходного типа и физическим внешним ключом к исходному PK. FK использует `ON DELETE NO ACTION`: удалить связанную исходную запись до удаления результатов будет нельзя. Если нужен только JOIN без этого ограничения, задайте `connect --no-foreign-key`. Перед публикацией проверяются исходные PK/адреса и идентичность endpoint/имени базы; другая конфигурация подключения отклоняется. Связь не изменяет исходную таблицу.

## Файлы без PostgreSQL

```sh
./bin/jana normalize --file addresses.txt --api-url http://localhost:8080
./bin/jana normalize --file addresses.json --no-interactive --quiet
./bin/jana normalize --run RUN_ID --output addresses.normalized.json
```

`connect` не требуется. Вход — UTF-8: текст с одним адресом на строку, JSON-массив строк, массив `{id, raw_address}` или объект `{records: [...]}`. `.json` распознаётся автоматически; для другого расширения укажите `--format json`/`--format lines`. Пробелы и пустые строки сохраняются; конечный перенос строки не добавляет лишнюю запись. В JSON `raw_address` должен быть строкой; ID — строкой или int64. Повторяющиеся ID остаются отдельными записями, числовые int64 сохраняются точно, включая после ручной правки. В браузере ID дополнительно отображается строкой без потери точности.

После `a` и подтверждения `y` появляется JSON `{results: [...]}` с нормализованными полями и диагностикой. По умолчанию — `<имя входа>.normalized.json` в текущем каталоге. Существующий файл не заменяется без `--force`; исходный снимок остаётся в журнале. Экспорт через сайт сохраняет локальные строки в формате `{rows, total}`; это вспомогательный формат проверки.

Служебные команды: `runs`, `serve --open`, `export --run RUN_ID`. Старые `postgres`, `import` и псевдоним `land` оставлены для совместимости. Публикация требует явного действия `a` → `y` либо `--confirm`.

## Отдельный контейнер / Compose

Из этой папки:

```sh
cp .env.example .env
# Настройте доступ к своей БД, URL API в локальном .env.
docker compose up --build -d --wait
```

Локальный интерфейс `http://localhost:8095` открывается без логина и пароля. Контейнер работает от UID 10001, журнал находится в томе `/data`. Обычные stop/restart/down сохраняют данные; `down --volumes` удаляет журнал и профиль.

Команды в уже работающем сервисе:

```sh
docker compose exec workspace /jana connect
docker compose exec workspace /jana normalize
docker compose exec workspace /jana normalize --run RUN_ID
```

Для файлов смонтируйте каталог входа/выхода в контейнер и укажите контейнерные пути. `docker compose run --rm -it workspace normalize` тоже использует общий том; работающий `serve` переиспользуется. Укажите `JANA_BROWSER_URL`, если браузеру нужен иной внешний адрес/порт; без `xdg-open` внутри контейнера CLI выводит ссылку для открытия вручную.

Для индивидуального контейнера используйте этот же образ `jana-cli:local`, том на `/data`, переменные подключения и `JANA_API_URL`. Команда по умолчанию — `serve --listen 0.0.0.0:8095`. Секреты можно монтировать файлами и указывать через переменные `*_FILE`. Для API за шлюзом поддерживается `JANA_API_TOKEN` (Bearer); он не включается в журнал. HTTP redirects к другому endpoint не выполняются.

Облачное тестирование использует тот же контейнер. Внешний listener требует пароль длиной минимум 16 символов; по умолчанию Compose публикует порт только на loopback. Для своего TLS-шлюза задайте точный `JANA_PUBLIC_ORIGIN` и нужный bind address. Никакого облачного развёртывания команда сборки не выполняет.

## Синтетический стенд

Из `cli/`:

```sh
docker compose -f compose.yaml -f compose.demo.yaml up --build -d --wait
```

Стенд добавляет отдельную PostgreSQL с пятью **синтетическими** строками в `public.orders` и настоящий API нормализации. Есть большой bigint, NULL, пустая строка, повтор адреса и перенос строки. У API демокаталог отключён; используется native libpostal с правилами и справочником. Пароль тестовой БД относится только к этому изолированному стенду. База не публикует порт на хост. `compose.demo.yaml` при сборке API использует его самостоятельный build context `../backend`; сборка самого CLI этого каталога не требует.

## Сохранение и публикация

- Источник первого варианта — обычная таблица с одиночным PK: smallint, integer, bigint, UUID, text или varchar; адрес — text/varchar. Составные ключи, представления и partitioned tables отклоняются. Числовой/UUID-тип сохраняется в `source_id` таблицы результата; varchar публикуется как text. Для источника PostgreSQL в JSON ключ строковый, поэтому int64 не теряет точность в браузере.
- Чтение идёт в PostgreSQL `REPEATABLE READ READ ONLY`, затем транзакция закрывается. Длительная ручная проверка не держит транзакцию источника. Локальный снимок ограничен 100 000 строками / 64 MiB входа, один адрес — 4096 байт; результаты хранятся в том же журнале без автоматического TTL. [Изоляция PostgreSQL](https://www.postgresql.org/docs/18/transaction-iso.html).
- Успешная порция сохраняется транзакцией SQLite до следующего запроса. При сбое API прогресс остаётся; кнопка возобновления отправляет только ещё не сохранённые строки. После аварии между ответом API и checkpoint допускается повтор этой порции.
- NULL источника сохраняется как NULL и не отправляется в строковый API. В результате такой записи — пустой raw для формы Result, явные null-поля и предупреждение `source_address_null`; исходное значение отдельно доступно в `row.raw_address`.
- Ручная проверка использует revision конкретной записи. Конфликт не перезаписывает форму. Изменение полей здания сбрасывает геопозицию и catalog links; confidence не повышается. Квартира/подъезд/этаж/ориентир остаются свойствами исходной записи. Подтверждение здания и выбор справочных кандидатов в этом интерфейсе пока не реализованы.
- Публикация берёт согласованный снимок источника на момент начала PostgreSQL-транзакции, проверяет все исходные PK/raw и атомарно записывает весь запуск. Изменённая/удалённая запись отменяет запись целиком. Позднейшие изменения источника требуют нового запуска: публикация не блокирует будущие обновления исходных адресов.
- Результат содержит типизированный `source_id`, `run_id`, точный nullable raw, 11 отдельных полей, confidence, координаты, статус, диагностику, reviewed и revision. Непроверенные строки сохраняются в журнале; CLI по умолчанию пропускает их при публикации. Произвольная существующая таблица не перезаписывается: принадлежность результата этой колонке проверяется по метке таблицы.
- Повтор публикации того же запуска не создаёт дубликаты. Если PostgreSQL commit прошёл, но локальный checkpoint не записался, повтор того же run заменяет только его строки. Полностью опубликованный локально запуск доступен для чтения; частично опубликованный остаётся открыт для проверки оставшихся записей.
- Права источника — SELECT и доступ к метаданным; целевая схема должна существовать и разрешать USAGE/CREATE. Для существующей таблицы результата нужны права чтения метки, INSERT/DELETE; при добавлении FK также владение таблицей результата и REFERENCES на исходный PK. `--no-foreign-key` отключает требование REFERENCES. Никакие права на UPDATE/DELETE исходной таблицы не требуются.

Пример чтения результата (укажите конкретный run):

```sql
SELECT o.id, n.city, n.street_name, n.house, n.apartment,
       n.reviewed,
       o.address IS NOT DISTINCT FROM n.raw_address AS source_is_current
FROM public.orders o
JOIN public.orders_jana_addresses n ON n.source_id = o.id
WHERE n.run_id = 'RUN_ID';
```

Журнал содержит приватные адреса и детали доставки. `var/`, `.env`, SQLite-файлы и тестовые артефакты исключены из Git/Docker context. Для резервной копии остановите сервис и скопируйте SQLite-файл. При открытии журнал обновляется для хранения исходных файловых ID; сохраняйте резервную копию перед обновлением. Интерфейс проверяет Host и Origin; пароль можно включить через `JANA_WEB_AUTH=password` и `JANA_WEB_TOKEN`; TLS предоставляет внешний шлюз. Это один операторский workspace, без разделения пользователей.

## Контракты и проверки

`api/normalization.openapi.json` — принятый снимок публичного backend-контракта. `api/openapi.json` описывает локальный orchestration API и принятые общие схемы. Go DTO генерируются из него, а не импортируются из backend:

```sh
python3 scripts/adopt-contract.py /path/to/downloaded/openapi.json
go generate ./internal/api
go test -race ./...
go vet ./...
```

Из корня `make generate` явно обновляет все принятые снимки. `make check` проверяет CLI, backend и основную SPA. `make cli-smoke` создаёт отдельный Compose-проект, проверяет PostgreSQL, восстановление/публикацию и desktop/mobile browser flow, затем удаляет только свои контейнеры/тома. Для browser-тестов нужен Node и установленный Chromium (`npm ci && npx playwright install chromium` из `cli/`); это инструменты разработки, не зависимости CLI/runtime. Самостоятельная сборка образа: `docker build -t jana-cli:local .`.

Начиная с комплекта v0.3.2, `street_name` сохраняет написание названия улицы из запроса; поиск справочника продолжает использовать разобранный компонент. Для автономного CLI обновите полный комплект, включая API. Ранее сохранённые запуски не пересчитываются автоматически: создайте новый запуск (`--new`).

## Обновление общей страницы

Из корня репозитория: `make generate`, затем `make cli-web`. Последняя команда независимо собирает `frontend/` и явно обновляет офлайн-снимок `cli/web/static/` и манифест исходников. `make check` обнаруживает устаревший снимок. Коммитить нужно сборку вместе с изменениями страницы. Самостоятельная сборка `cli/` использует готовый снимок, не читает соседние каталоги и не требует Node. `/config.js` задаётся локальным сервером; вкладка с `?run=...` из CLI открывает тот же workspace, что и основная страница.

В wizard доступны ручной ввод и предварительный просмотр TXT/JSON/CSV перед запуском (до 1 000 адресов / 2 MiB). Сохранённые запуски CLI могут содержать до 100 000 записей; страница читает их по 50, сохраняет NULL, исходные ID и ревизии строк. Чтобы создать новый пакет из wizard, нажмите «Сбросить». Файловые запуски публикуются клавишей `a` в `jana normalize`, а запуски PostgreSQL публикуются явно в отдельную таблицу.

## Открыть веб-интерфейс с другого устройства через Tailscale

На машине с работающим CLI можно проксировать только веб-порт внутрь tailnet:

```sh
sudo tailscale serve --bg --http=8095 http://127.0.0.1:8095
```

Используйте полный адрес, который напечатает Serve (`http://<машина>.<tailnet>.ts.net:8095/`). В локальном `cli/.env` задайте `JANA_PUBLIC_ORIGIN` равным этому origin **без завершающего слеша**, а `JANA_BROWSER_URL` — URL со слешем; затем `./cli/jana up`. Сервис принимает этот внешний Host только при явно настроенном origin и пароле веб-интерфейса длиной не меньше 16 символов либо явном `JANA_WEB_AUTH=none`. Неизвестные Host/Origin продолжают отклоняться. При `JANA_WEB_AUTH=password` вход: `jana` / ваш `JANA_WEB_TOKEN`.

Веб-страницы и запросы чтения/сохранения локальных заданий идут через 8095. API нормализации на 8080 отдельно открывать не требуется: CLI вызывает его с той же машины. Serve работает в фоне внутри tailnet, без публичного Funnel. Выключить этот проброс: `sudo tailscale serve --http=8095 off`. Подробнее: [Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve).

## Состояние CLI в вебе и SSE

Ссылка в терминале и действие W включают `?run=ID`: открывается именно выбранный запуск CLI. При открытии корня сайта без параметров автоматически загружается последний сохранённый запуск из локального SQLite-журнала. Новый ввод доступен через «Сбросить».

`GET /v1/events` отправляет SSE-события `runs` с метаданными RunList: начальный снимок, затем обновления после сохранённых пакетов, исправлений и публикации. Сервер следит за ревизиями SQLite, поэтому видит изменения из других процессов CLI, а не только своего worker. При переподключении приходит актуальный снимок. Браузер перечитывает только выбранную страницу изменившегося запуска; опрос локальных заданий таймером удалён. Открытый редактор сохраняет исходную ревизию и черновик, обновления очереди применяются после его закрытия.

Локальный интерфейс и переносимые Compose-файлы по умолчанию используют `JANA_WEB_AUTH=none` и открываются без пароля. При необходимости задайте `JANA_WEB_AUTH=password` и `JANA_WEB_TOKEN`. При прямом запуске `serve` с внешним listener по умолчанию требуется пароль длиной не меньше 16 символов. Для reverse proxy при отключённом пароле по-прежнему нужно указать точный `JANA_PUBLIC_ORIGIN`; чужие Host/Origin отклоняются. Эта настройка не передаётся API нормализации.

### Подключение и публикация

`./cli/jana connect -w` (или `--web`) открывает веб-мастер. Сначала проверяется доступ к PostgreSQL, затем выбираются таблица и текстовая колонка; первичный ключ определяется автоматически. Пароль передаётся только локальному CLI-сервису и сохраняется в профиле с правами 0600, без передачи нормализатору. В браузере пароль не сохраняется. `Ctrl+C` отменяет ожидание мастера.

В терминальном `connect` таблица и колонка выбираются стрелками ↑/↓ с подтверждением Enter; имена с `address` располагаются первыми. Все параметры по-прежнему можно передать флагами с `--no-interactive`.

`./cli/jana normalize` показывает обработку, проверку и публикацию в едином экране. Исходные строки не изменяются; готовые результаты записываются в таблицу назначения. Непроверенные адреса остаются в журнале для продолжения. После полной публикации браузер показывает записанные строки из PostgreSQL с постраничным просмотром.

Повторный `connect` показывает сохранённый профиль (пользователя, хост, порт, базу, источник и таблицу результата) и дату последней проверки. Enter принимает прежние параметры, включая выбранные таблицу и колонку. В `connect --web` те же значения подставляются автоматически; сохранённый пароль остаётся на стороне CLI. Пустое поле использует его только для того же хоста, порта, базы и пользователя. Для смены или очистки пароля введите новый либо снимите флажок использования сохранённого. Сохранённый профиль проверяется заново при продолжении мастера.

В обычном терминале `connect` показывает пошаговые поля и списки в стиле create-vite: ↑/↓ (или J/K), Home/End и Page Up/Down перемещают выбор, Enter подтверждает сохранённое значение. В текстовых полях работают ←/→, Home/End, Backspace/Delete и Ctrl+U для очистки; пароль показывается точками. Ctrl+C или Esc отменяет мастер и восстанавливает настройки терминала. Длинные списки прокручиваются вокруг текущего выбора. При вводе через pipe или `TERM=dumb` остаётся построчный режим с номерами; флаги `--no-interactive` работают как раньше. `NO_COLOR` отключает цвет.

Сообщения, справка и статусы Jana отображаются на русском языке. Команды, флаги, SQL-идентификаторы и машинные JSON-коды остаются прежними. При публикации доступны «подтвердить» и «отмена»; `confirm` и `cancel` сохранены для совместимости со скриптами.

На странице опубликованного результата «Новый запуск» открывает пустую форму. Пункт «Тестовый запуск» в навигации также открывает её. URL `/?new=true` сохраняет этот выбор после перезагрузки; обычный `/` по-прежнему восстанавливает последний запуск CLI, а ссылки с `?run=…` или `?job=…` открывают конкретный запуск.

## Проверка перед публикацией в терминале

На обычном TTY `jana normalize` открывает полноэкранный рабочий экран. В заголовке — короткий ID, источник, счётчики запуска, страницы, поиск и сортировка; во время разбора — прогресс, после завершения — общее время и среднее на запись второстепенным текстом. Список показывает исходный адрес, цветной статус, уверенность в процентах и различия состава адреса. Детали раскрывают полный результат, причины и точный ID. При ошибке нормализации `r` продолжает разбор с сохранённой позиции. Публикация и подтверждения доступны после завершения обработки.

| Клавиша | Действие |
| --- | --- |
| j / ↓ / N / PgDn | Следующая страница |
| k / ↑ / P / PgUp | Предыдущая страница |
| g | Перейти на страницу по номеру |
| / | Поиск по адресу, области или населённому пункту; пустой запрос сбрасывает поиск |
| f | Только требующие проверки / все записи |
| s | Сортировка по номеру, статусу, региону или уверенности |
| Tab / →, Shift+Tab / ← | Выбор записи внутри страницы |
| Enter / v / щелчок | Полный адрес, нормализация, причины и точный ID |
| c | Просмотреть и подтвердить выбранный результат через y |
| e | Редактировать поля адреса в терминале |
| w | Открыть веб-редактор и показать полную ссылку |
| r | Повторить прерванный разбор |
| x / X | Экспорт страницы / всего отфильтрованного списка в JSON или CSV |
| a | Предпросмотр состава публикации; y — явно записать готовые записи |
| q | Сохранить журнал и выйти; выполненные публикации сохраняются |
| ? | Справка; Esc возвращает к списку |

Стрелки и колесо в деталях прокручивают текст. Поиск поддерживает регистр русского и казахского Unicode; % и _ означают обычные символы. Регион и статус — варианты сортировки, а не изменение результатов нормализации. «По уверенности» — удобный порядок для просмотра, не измеренная вероятность ошибки.

Страница содержит --page-size 20 записей (допустимо 1–100). Небольшое окно показывает часть страницы, выбор Tab/←/→ прокручивает её; количество страниц не меняется при изменении размера окна. --search, --review-only и --sort position|status|region|risk задают начальный вид. --verbose раскрывает полный ID, --no-color или NO_COLOR отключают цвета. --plain, перенаправленный stdin или TERM=dumb используют построчный режим; --confirm оставляет явную автоматизацию без TUI. В runtime используется Go-библиотека [tcell](https://pkg.go.dev/github.com/gdamore/tcell/v2@v2.8.1), Python и runtime-загрузки не нужны.

По умолчанию CLI публикует **все готовые записи данного запуска**: автоматически нормализованные и подтверждённые оператором. Текущая страница, поиск и фильтр не ограничивают публикацию. Остальные строки остаются в журнале и попадают в итоговый счётчик «пропущено». Полная старая публикация, включая неподтверждённые, остаётся доступна явно через --ready-only=false в построчном режиме; HTTP API сохраняет прежнюю полную публикацию. Экспорт x/X не подтверждает записи и не меняет таблицу результата; существующий файл экспорта не перезаписывается.

После частичной записи запуск остаётся открытым. Повторный normalize начинает с очереди неподтверждённых адресов; f позволяет показать весь снимок. Пока запуск незавершён, обычный normalize с тем же сохранённым подключением, источником, API и таблицей результата продолжает **тот же журнал**; normalize --run ID выбирает его явно. normalize --new создаёт новый снимок. Данные другой базы, источника или API не переиспользуются. Это продолжение работы с существующим журналом, а не кэш ответов нормализации.

Каждая следующая публикация транзакционно заменяет строки только того же run_id полным текущим набором готовых записей, сохраняя ранее готовые строки без дубликатов (run_id, source_id). Тип ключа, проверка источника и проверка версии сохраняются. Когда готов весь снимок, запуск закрывается как опубликованный. JSON-файлы частичного запуска также содержат только готовые записи; для замены ранее созданного итогового файла требуется явный --force.

Прогресс отражает подготовленные записи в транзакции и остаётся ниже 100% до успешного завершения. Итог отдельно показывает автоматические, ручные и пропущенные записи. Ошибка или изменение версии не выдаёт успешный итог.

В текстовой форме `e`: Tab / Shift+Tab и ↑↓ переключают поля, ←→ / Home / End перемещают курсор. Ctrl+S сохраняет поля и подтверждает запись оператором; Esc отменяет весь черновик. Ctrl+U задаёт пустую строку, Ctrl+N — NULL; нетронутые значения сохраняют исходный смысл. Все 11 полей доступны, длинные значения прокручиваются. Устаревшая версия не перезаписывает более свежую правку: черновик остаётся на экране, для загрузки новой версии выйдите через Esc и снова нажмите e. Публикация остаётся отдельным действием a → y.

Экран ссылки по `w` использует терминальную гиперссылку OSC 8 с полным URL, включая при переносе на несколько строк. На этом экране перехват мыши отключён: терминал обрабатывает Cmd+Click / Ctrl+Click и выделение текста. Esc возвращает навигацию мышью по списку. Открытие ссылки зависит от поддержки OSC 8 и настроек терминала; полный URL остаётся доступен для копирования.

Процент рядом со статусом строки — исходная уверенность нормализатора; до получения результата выводится прочерк. Подтверждение оператором и редактирование не заменяют эту оценку на 100%. Уверенность также видна в деталях и текстовой форме редактирования.

Локальная версия использует тот же `CityCandidatePicker` и тот же движок справочника, что публичный сайт. Откройте запись и выберите населённый пункт, область и тип по совместимым вариантам. В терминале `normalize` клавиша `l` открывает справочник для выбранной записи; ↑↓ выбирают вариант, Enter пересчитывает исходный адрес, Esc отменяет. Выбор сохраняется по позиции записи, проверяет ревизии журнала/строки и версию справочника, сохраняет точные входные ID, сбрасывает полную операторскую проверку и не подтверждает здание. Другая запись с тем же ID не меняется. Нужна версия API с `/v1/normalize/candidates` и `/v1/normalize/selections`; старый API выдаёт явную ошибку с предложением обновления.
