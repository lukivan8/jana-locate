# Массовая нормализация существующей базы

Продуктовое решение от 16 октября 2026 года. Статус: план расширения; сохраняемые задания и ручная проверка реализованы в первом варианте ([API и ограничения](../backend/docs/jobs.md)); локальная CLI для Postgres реализована в первом варианте ([запуск и ограничения](../cli/README.md)). Доступ к БД принадлежит CLI, а не сервису нормализации.

## Основание и приоритет

В локальном извлечении финального ТЗ явно описана проблема: адрес уже хранится в базе одной строкой, что мешает аналитике по городам, определению зоны доставки и работе курьера. Основной сценарий Jana Locate — массовое преобразование этих строк в структурированные поля с проверкой неоднозначных результатов. Единичный разбор на карте служит проверкой конкретного примера и объяснением результата.

Пакетный API и загрузка файла требуются ТЗ. Подключение к Postgres — наше расширение, а не установленное требование организаторов. Его польза для реального внедрения — гипотеза, которую нужно показать работающим сквозным примером. Точность разбора и обязательный offline-прогон сохраняют приоритет.

## Основной сценарий

1. Оператор запускает CLI в своём окружении и указывает локально настроенное подключение Postgres, таблицу, первичный ключ, колонку адреса и URL API нормализации. API может работать в соседнем Docker-контейнере или удалённо.
2. CLI проверяет доступ, показывает предпросмотр и создаёт локальный рабочий запуск. Она поднимает на loopback HTTP API и встроенный статический интерфейс проверки, затем по флагу открывает браузер. Основная SPA остаётся отдельным приложением; CLI собирается без её исходников.
3. CLI читает адреса порциями, вызывает публичный пакетный API и сохраняет вход, результаты, прогресс и соответствие исходным ключам в локальном журнале. Сайт обращается к локальному API проверки. Сервис нормализации получает только записи для разбора; подключение к БД ему не передаётся.
4. Оператор фильтрует спорные строки, видит исходную строку рядом с разобранными полями и сохраняет исправления. Сохранённые правки переживают обновление страницы и рестарт CLI. Выбор справочных кандидатов добавляется отдельно: этот endpoint пока не реализован.
5. После проверки оператор видит сводку и даёт команду публикации. CLI проверяет актуальность источника и записывает результаты в отдельную связанную таблицу Postgres. Исходная колонка не изменяется. Файловый импорт/экспорт остаётся альтернативным способом работы.
6. Потребитель получает адресные поля через соединение по исходному первичному ключу и конкретному опубликованному запуску. Непроверенные результаты явно отмечены; ошибки и неизвестные поля не пропадают из выгрузки.

Проверка пакетная: фильтры по причинам неопределённости, переход между спорными строками, счётчики проверенных и оставшихся записей. Каждая строка не требует обязательного ручного открытия. Высокая эвристическая уверенность сама по себе не означает подтверждения оператором.

## Граница CLI и API

Postgres-драйвер, соединение с БД и операции чтения/публикации принадлежат локальной CLI. Учётные данные разрешаются в окружении заказчика и не передаются сервису нормализации, браузеру, публичному конфигу, URL или журналам. Backend нормализации не получает доступ к клиентской базе.

CLI — самостоятельный потребитель публичного HTTP API и готовый пример интеграции. Заказчик может развернуть API из Docker и написать свой потребитель; использование CLI не является обязательным условием нормализации. URL API настраивается, чтобы одинаково поддерживать локальный контейнер и удалённый сервис.

Локальный компонент CLI владеет бизнес-логикой запуска: чтением источника, пакетированием, хранением состояния, правками и публикацией. Он предоставляет собственный HTTP-контракт встроенному интерфейсу проверки и не добавляет server functions или доступ к БД в основную SPA. Готовые статические файлы сайта должны поставляться с CLI или заранее подготовленным комплектом; Node и сборка frontend при запуске оператора не требуются.

Для этого сценария журнал запуска и ручные правки хранятся локально независимо от удалённого API. Уже реализованные серверные задания можно использовать в обычном веб-сценарии; CLI не должна зависеть от их семидневного TTL для сохранности длительной локальной проверки. Удалённый API можно вызывать через существующий синхронный `/v1/normalize`. Исходные PK связываются с позициями результатов локально; передавать имена таблиц или параметры подключения для нормализации не требуется.

Первый поддерживаемый источник — обычная таблица с простым первичным ключом и текстовой колонкой. Таблицы без PK и составные ключи отклоняются с понятным объяснением до запуска. Имена схем, таблиц и колонок проверяются по метаданным и безопасно экранируются; значения передаются параметрами. Произвольный SQL не является частью первого интерфейса.

Права чтения источника и записи результата разделены. Проверка доступа к целевой схеме выполняется до обработки; отсутствие права создавать таблицу не должно обнаруживаться после длительного прогона. Подключение к локальной БД совместимо с offline runtime: внешние геокодеры и загрузка моделей не нужны.

## Связанная таблица

Рабочее имя результата — `jana_normalized_addresses`; окончательное имя и схема выбираются перед публикацией. Минимальный состав:

| Поля | Назначение |
| --- | --- |
| `run_id`, `source_id` | Уникальная пара: запуск и исходная запись; тип `source_id` соответствует PK источника |
| `raw_address` | Точная строка на момент чтения; нужна для проверки и выявления изменений |
| Адресные поля | Поля действующего контракта, включая квартиру, подъезд, этаж и ориентир; неизвестное — `null` |
| `confidence`, диагностика | Результат алгоритма и причины необходимости проверки |
| `review_status`, `revision` | Состояние проверки и защита от перезаписи конкурентных правок |
| Версии алгоритма и справочника, время обработки/проверки | Воспроизводимость результата и происхождение правок |

Связь по PK позволяет делать JOIN. Физический внешний ключ — отдельный выбор при публикации: он влияет на удаление исходных строк, поэтому не создаётся молча. Не выбирать «последний результат» неявно: потребитель указывает опубликованный `run_id`.

## Надёжность и границы хранения

- При начале обработки фиксируется входной снимок задания. Длительное чтение большой таблицы должно иметь документированную стратегию согласованности; пагинация по PK сама по себе не даёт единого снимка.
- Перед публикацией проверяются удалённые и изменённые исходные строки. Устаревшие результаты отмечаются и требуют решения оператора; нельзя представить разбор старого адреса как актуальный.
- Пустые/NULL-адреса и ошибки учитываются отдельно без потери связи с исходной записью. Правило для NULL задаётся адаптером, поскольку API принимает строку.
- Задание возобновляется после сбоя с сохранённой позиции и revision. Повтор публикации того же запуска не создаёт дубликатов; частично записанный результат не считается опубликованным. Публикация использует staging и атомарное переключение состояния запуска.
- Новый прогон не стирает ручные правки предыдущего. Перенос правок между запусками требует явной проверки исходной строки и контекста справочника.
- Данные задания — временное состояние работы с определёнными лимитами и сроком хранения. Опубликованная таблица — результат заказчика. Ни то ни другое не используется как кеш ответов на будущие строки.
- Проверка адреса и подтверждение здания в каталоге — разные действия. Квартира, подъезд, этаж и ориентир остаются в результате исходной записи и не становятся свойствами здания.
- Пароли, входные снимки, результаты и рабочие таблицы не включаются в Git, публичные образы и демонстрационные данные.

## Порядок реализации и приёмка

1. Сохраняемое пакетное задание и правки: развить [план выбора кандидатов](address-review-jobs.md), определить ограничения объёма, хранение, удаление и восстановление. Существующий синхронный `POST /v1/normalize` сохранить.
2. Массовая очередь проверки: фильтры, прогресс, сохранение исправлений и экспорт без потери исходных ID/строк. Карта остаётся инструментом изучения отдельного адреса.
3. Локальная CLI: конфигурация доступа к Postgres и URL API, предпросмотр, чтение порциями, локальный журнал с восстановлением; вызов публичного API без передачи доступа к БД. Лимит 1000 записей одного API-пакета не должен ограничивать весь локальный запуск.
4. Локальный сайт: поставка готовой SPA с CLI, loopback API для состояния и проверки, сохранение исправлений в локальном журнале.
5. Публикация силами CLI: связанная таблица, проверка актуальности, повторяемая запись и пример JOIN для потребителя.

Сквозная демонстрация на синтетической БД: выбрать колонку → обработать пакет → исправить неоднозначную строку → перезапустить CLI → увидеть сохранённую локальную правку → опубликовать → получить её через JOIN. Дополнительно проверить сбой/возобновление, повтор публикации, изменение исходной строки, NULL, недостаточные права и неизменность источника. Frontend проверяется в браузере desktop/mobile с временным overlay; изменения контракта начинаются с OpenAPI и проходят `make generate` / `make check`.

Дополнительная приёмка CLI: один сценарий работает с API в соседнем контейнере и с удалённым URL; API не получает DSN/пароль или доступ к БД; потеря API не удаляет локальный запуск и исправления; возобновление не повторяет успешно сохранённые пакеты; сайт запускается без Node и без runtime-загрузок. Первый вариант CLI и локального интерфейса реализован; составные PK, справочный выбор кандидатов и автоматическое отслеживание новых записей остаются расширениями.

### Реализованный интерфейс CLI

`connect` проверяет доступ и сохраняет локальный профиль (интерактивный мастер или флаги). `normalize` автоматически предлагает подключение при отсутствии профиля, показывает прогресс/результаты и открывает локальный сайт по W. `normalize --run ID` продолжает сохранённый запуск; `--no-interactive --quiet` подходит для автоматизации. `land` показывает предпросмотр и записывает связанную таблицу только после `confirm`; новый профиль по умолчанию создаёт FK, `--no-foreign-key` оставляет JOIN. `normalize --file` принимает построчный UTF-8 и JSON без подключения к БД; `land --output` сохраняет итоговый JSON. Подробности и ограничения — в [CLI README](../cli/README.md).
