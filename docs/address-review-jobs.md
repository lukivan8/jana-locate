# Пакетная нормализация с выбором неоднозначных кандидатов

Реализовано 16 октября 2026. Действующий контракт и ограничения: [backend/docs/jobs.md](../backend/docs/jobs.md). Продуктовый контекст: [массовая нормализация базы](bulk-normalization.md).

## Поток

1. `POST /v1/normalization-jobs` принимает прежний массив или `{records:[...]}` и возвращает `202` с сохранённым заданием.
2. Браузер опрашивает `GET /v1/normalization-jobs/{job_id}` до завершения. Тот же ответ содержит обычные результаты; отдельный `/results` не требуется.
3. Оператор открывает запись. UI запрашивает `GET /v1/normalization-jobs/{job_id}/records/{record_index}/candidates` и показывает исходные сущности, области и источники.
4. Оператор выбирает населённый пункт. `POST .../selections` передаёт `entity_id`, `expected_revision` и `reference_version`.
5. Backend заново разбирает исходную строку с ограничением на выбранную сущность, восстанавливает область и пересчитывает зависимые поля, связь со зданием, координаты и confidence. Возвращает обновлённое задание.
6. Выбор сохраняется в журнале и восстанавливается при повторном открытии или рестарте. Проверка остальных полей и подтверждение здания с координатами остаются отдельными действиями.

`record_index` — исходная позиция с нуля. Повторяющиеся пользовательские ID не объединяются. Точный raw, порядок и тип ID, включая int64, сохраняются. Старый синхронный `POST /v1/normalize` сохраняет поведение и оба формата запросов/ответов.

## Пример Караганды

Расширенный OSM содержит положительный факт `Караганда, Алалыкина 12`, который теперь автоматически уточняет населённый пункт. Для неизвестного номера `Караганда, Алалыкина 999999` неоднозначность сохраняется:

| Кандидат | Область | ID источника |
| --- | --- | --- |
| Караганда — город | Карагандинская область | КАТО 351010000 |
| Караганда — село | Актюбинская область | КАТО 154247300 |

После выбора города область становится Карагандинской; предупреждение об этой неоднозначности снимается. Район и координаты неизвестного здания остаются null. Выбор не повышает confidence автоматически до 100% и не отмечает всю запись проверенной. Тип населённого пункта берётся только из явного квалификатора источника, без оценки популярности названия.

## Гарантии и границы

- Кандидаты выводятся из исходной строки и локального immutable справочника. Указанная область ограничивает список. Нельзя выбрать произвольную сущность или молча стереть конфликт нескольких областей/населённых пунктов.
- Выбор передаётся как ID, не как дописанный текст в raw. Нормализация выбранной записи выполняется заново; старые ручные исправления **этой записи заменяются**. UI сообщает об этом перед действием и блокирует выбор при несохранённом черновике. Другие записи не меняются.
- Старые координаты/catalog ID не переносятся в новый административный контекст. Подтверждённое здание с одноимённым городом принимается только при совместимой известной области.
- Ошибки конкурентных правок и смены справочника возвращаются явно как `409`. Версия справочника — SHA-256 полного immutable SQLite. Повтор последнего выбора идемпотентен, пока последующие правки не изменили ревизию.
- Это состояние проверки конкретного задания, а не answer cache для будущих совпадающих raw или ID. Журнал отделён от building overlay, ограничен 7 днями/50 заданиями/64 MiB. Выбор не вызывает catalog confirmations.
- Runtime остаётся offline; внешние источники загружаются только при подготовке snapshot. Незавершённое задание после рестарта обрабатывается с текущим snapshot; фиксация исходной версии моделей для него пока не реализована.

## Проверки

Go-тесты проверяют одноимённые населённые пункты, несовместимую область, два разных города в строке, смену города и сброс геокода, точный raw/int64/duplicate IDs, stale revisions/snapshots, идемпотентность, восстановление журнала и совместимость синхронного API. Playwright проверяет выбор/смену, восстановление после reload, конкурирующую вкладку и экспорт на 1440px и 390px. Docker smoke проверяет выбор и сохранение после рестарта вместе с 1000-record batch и building confirmations.
