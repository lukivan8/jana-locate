# Аудит нормализации и batch: 16 октября 2026

> Исторический отчёт до удаления GLiNER 16 октября 2026. Упоминания модели, команды и замеры ниже относятся к прежнему пайплайну. Сейчас работают libpostal, правила и КАТО/OSM; код сервиса, его настройка и штраф за недоступность удалены. Эти старые измерения не описывают текущую скорость или точность.


Текущий API принимает пакетные запросы, но корректность разбора всех адресов и географическая точность не подтверждены. Воспроизведены ошибки официального sample и два небезопасных выбора здания на искусственном каталоге. Основной измеренный расход времени — GLiNER, при этом в текущей конфигурации он не добавил ни одного адресного поля на проверенном наборе.

Изменены только инструменты измерения и документация. Рабочий пайплайн, контракт, модели и эксплуатационный overlay не менялись.

## Что проверено

- 30 открытых синтетических случаев в `backend/internal/normalize/testdata/audit.synthetic.json`: явные и обратные маркеры, дроби/литеры, микрорайоны, двуязычность, ориентиры, административные конфликты, пропуски, невидимые символы.
- Один локальный sample организаторов с эталонным выходом. Это весь доступный размеченный материал организаторов, не train. Содержимое sample и производные результаты сохранены только в игнорируемой `.artifacts/normalization-audit/`.
- Настоящий native libpostal с подготовленными моделями, настоящий CPU GLiNER через внутренний HTTP, справочник с 17 242 сущностями. `AllowDemo=false`, новый временный overlay. В прогоне качества нет координат из synthetic seed.
- Восемь вариантов состава пайплайна и отдельно отключение `Working`. Предсказания моделей фиксировались один раз и использовались повторно при отключении этапов. Для варианта без очистки получены отдельные настоящие предсказания на исходных строках.
- Размеры batch 1, 8, 32, 128, 1000; чанки GLiNER 8, 32, 128; рост каталога до 10 000 зданий; 10 проверок безопасности геокодера на отдельном временном каталоге с искусственными координатами.
- HTTP: массив и объект с `records`, 1000 пустых строк с сохранением большого числового ID, отказ для `null` вместо адреса и 1001 записи.

Это диагностический набор, составленный для поиска дефектов. Он не репрезентативен по частотам реального потока; результаты не являются оценкой скрытой метрики. Ожидания включают некоторые восстановленные административные поля, поэтому таблица не воспроизводит официальное взвешенное оценивание. Реальных эталонных координат нет: физическую точность геокодирования этот аудит не измеряет.

## Текущая архитектура

```text
HTTP: строгая валидация, 1..1000 записей, 2 MiB, 4096 байт/адрес
  → один snapshot каталога зданий на запрос
  → Working: невидимые символы и пробелы, исходная строка сохраняется
  → native libpostal последовательно, с глобальным mutex
  → regex независимо добавляет evidence
  → GLiNER: последовательные HTTP-чанки по 32
      → CPU model, int8, 2 threads, microbatch=8, глобальный lock
      → длинные строки: окна 256 символов с шагом 192
  → reconciliation каждого адреса в Go:
      aliases + иерархия КАТО/OSM → конкурирующие поля → каталог зданий
  → поля, nullable координаты, эвристический confidence, status, warnings
```

Распознавание компонентов и поиск координат — разные задачи. КАТО/OSM содержит административные и уличные сущности, но не координаты зданий. Единственный источник координат — подходящая запись каталога. OSM ограничен частью Астаны; это не покрытие улиц Казахстана. Synthetic seed исключён по умолчанию. Поэтому отсутствие координат для распознанного адреса сейчас ожидаемо.

Положительные свойства: сохраняются порядок, ID и raw; поля могут извлекаться без здания; неоднозначность обычно ведёт к отказу от координат; детали доставки не становятся свойствами здания; GLiNER проверяется по Unicode spans; runtime не требует внешнего геокодера.

## Вклад этапов в качество

Ниже только 30 открытых синтетических случаев, без sample организаторов. Проверяются все 11 адресных полей. 116 эталонных значений непустые, 214 ожидаются `null`. Строковые поля сравниваются через `reference.Canon`; числовые идентичности — строго с сохранением дроби, дефиса и литеры. «Лишние поля» — ненулевое значение там, где эталон ожидает `null`. Полностью правильная запись совпадает во всех 11 полях по этим правилам сравнения.

| Вариант | Правильные непустые значения / 116 | Лишние поля | Полностью правильные записи / 30 |
| --- | ---: | ---: | ---: |
| Полный пайплайн | 95 | 4 | 18 |
| Без GLiNER | 95 | 4 | 18 |
| Без libpostal | 90 | 3 | 18 |
| Без КАТО/OSM | 90 | 2 | 17 |
| Без regex | 52 | 6 | 4 |
| Без очистки Working | 94 | 4 | 17 |
| Только regex | 82 | 0 | 17 |
| Только libpostal | 48 | 2 | 3 |
| Только GLiNER | 0 | 0 | 3 |

Regex — главный положительный вклад, но также источник сильных ошибочных гипотез. Libpostal и справочник добавляют по пять правильных непустых значений при сравнении с полным вариантом; одновременно иногда добавляют ошибки. Их удаление не обосновано. Working исправляет конкретный случай невидимых символов и почти ничего не стоит.

GLiNER при штатных метках и пороге 0.25 вернул пустые списки сущностей для всех 31 проверенного адреса. Его отключение не изменило ни одного из 11 полей; warnings и confidence при этом меняются. Это вывод о проверенной конфигурации и наборе, а не доказательство бесполезности GLiNER вообще. Успешный `/readyz` подтверждает готовность процесса, а не полезность его предсказаний.

### Изолированное сравнение FP32 и int8

Запущены отдельные процессы одного и того же подготовленного образа, с теми же весами, `microbatch=8`, 2 CPU и без сети. Менялся только флаг квантования. Здесь 29 непустых рабочих адресов и два контрольных текста: русский адрес и английская фраза. Пустые строки исключены, как в HTTP runtime.

| Метки и порог | FP32: сущностей | int8: сущностей | FP32 / int8 время inference, с |
| --- | ---: | ---: | ---: |
| Штатные английские, 0.25 | 101 | 0 | 3.52 / 2.54 |
| Штатные английские, 0.10 | 137 | 0 | 3.80 / 2.72 |
| Русские, 0.25 | 109 | 0 | 2.93 / 1.95 |

В этой Linux x86 CPU-конфигурации текущая dynamic int8 quantization подавляет выдачу модели. Простой подбор threshold/labels проблему не устраняет. В FP32 контрольный город Астана получает score около 0.98. Это локализует проблему в режиме квантования, но ещё не устанавливает конкретную неисправную операцию/backend и не измеряет точность всех 101 сущности. Старый сохранённый профиль macOS/int8 с ненулевыми предсказаниями не переносим на текущий Linux runtime.

После этого выполнен настоящий полный прогон через отдельный внутренний FP32-сервис, включая все варианты отключения этапов и batch на 1000 строк. На тех же 30 открытых случаях:

| Вариант с FP32 evidence | Правильные непустые значения / 116 | Лишние поля | Полностью правильные записи / 30 |
| --- | ---: | ---: | ---: |
| Полный FP32 пайплайн | 94 | 10 | 17 |
| Без GLiNER | 95 | 4 | 18 |
| Без libpostal | 94 | 9 | 18 |
| Без КАТО/OSM | 91 | 7 | 16 |
| Без regex | 42 | 18 | 4 |
| Без Working | 92 | 12 | 16 |
| Только GLiNER FP32 | 15 | 6 | 3 |

**Включить FP32 вместо int8 недостаточно для улучшения качества.** На этом наборе добавление модели уменьшает число правильных непустых значений на одно и добавляет шесть лишних полей. В частности, название квартала становится районом, слитная улица с домом — городом, а в официальном sample появляется ложный этаж. Нужны подбор схемы меток/обучение и более строгая проверка evidence по роли и spans. Вклад libpostal тоже зависит от состава пайплайна: в FP32-конфигурации его отключение здесь не уменьшило число правильных непустых значений. Этапы нельзя считать независимыми улучшениями.

Суммарное совпадение 311/341 полей на наборе с sample выглядит высоким из-за многочисленных `null`. Для решений полезнее смотреть на непустые значения, лишние поля и полностью правильные строки, как в таблице выше.

## Воспроизведённые ошибки разбора

1. **Микрорайон с номером и отдельным домом.** Для открытого случая `Мкр Аксай 3а, 59, кв 70` результат содержит `street_name=Аксай`, `house=3а`. Libpostal сам предлагает дом `59` и дорогу `мкр аксай 3а`, но regex трактует окончание имени как дом. Вес regex 0.94 превосходит 0.66 у libpostal. Та же категория ошибки воспроизводится на локальном официальном sample.
2. **Обратные маркеры с пробелом.** `5 подьезд`, `239 кв`, `9 этаж` не поддерживаются полноценно. В цепочке `Нурсити 2 микрорайон 11дом 5 подьезд 239 кв` получены улица `2`, дом `5`, подъезд `239`. Forward-regex читает следующее число как значение предыдущего маркера.
3. **Слитная улица и дом.** `Назарбаева8` не даёт ни улицу, ни дом на текущем наборе.
4. **Микрорайон рядом с улицей.** В `Алматы, микрорайон Аксай 3а, улица Новая 12` выбирается первый микрорайон вместо отдельной улицы; `living_area` не заполняется.
5. **Ориентир становится городом.** `Qazpost Солнечный` не выделяется как landmark; справочник восстанавливает населённый пункт Солнечный и Павлодарскую область. Для `магазин Береке` также появляется ложный город Береке. Поиск административных упоминаний не ограничен ролью текстового фрагмента.
6. **Двуязычный город.** На sample город остаётся склеенным с маркером и вторым названием. Очистка городского префикса есть в `modelSignal`, но не симметрично для postal evidence. Высокий confidence не предотвращает эту ошибку.
7. **Отрицательный этаж.** `этаж -1` теряется, хотя числовой floor должен допускать подземные этажи, если это входит в целевой контракт данных.

Официальный sample принимается обоими HTTP-форматами, но отличается от эталона по пяти адресным полям. Два из них — отсутствующие восстановленные административные сведения; остальные затрагивают непосредственно разбор. Совместимость JSON не означает корректность нормализации.

## Безопасность геокодирования

Тестовый каталог содержит два искусственных здания с одной улицей/домом в разных городах. Координаты вымышленные и служат только индикатором выбора записи. 8 из 10 проверок соблюдают заданное безопасное поведение:

- Явный совместимый город разрешает здание; без города два кандидата не дают координат.
- Неизвестный город/дом, квартира вместо дома, конфликт городов, несовместимый тип улицы и дробный дом вместо целого не приводят к ложному выбору.

Два случая требуют исправления до заявления о безопасном геокодировании:

| Вход | Фактический результат | Причина риска |
| --- | --- | --- |
| `Астана, улица Тестовая дом 12 дом 13` | `matched`, дом 12, координаты | Парсер берёт первое явное совпадение и удаляет все совпадения; конкурирующий дом не доходит до reconciliation |
| `Астана, улица Тестовая дом 12, корпус 2` | `matched`, координаты базового дома 12 | Корпус не входит в компоненты и идентичность каталога; отдельное строение нельзя проверить |

Это доказательства недостаточной защиты при сопоставлении, а не измерения ошибки в метрах. Если корпус нельзя выразить в текущем контракте, безопасное промежуточное поведение — предупреждение и отказ от уверенного выбора отдельного здания.

## Производительность batch

Linux amd64, AMD Ryzen 5 4600H; текущий GLiNER-контейнер ограничен 2 CPU и 3 GiB. Native Go-аудит выполнялся на хосте. Модели уже прогреты; загрузка не включена. Набор на 1000 записей циклически повторяет 31 диагностическую строку. Это fixture throughput, не реальный train. Прогоны однократные, сервис общий, короткие параллельные диагностические обращения могли влиять на времена; p95/p99 и предельная конкурентная нагрузка не измерены.

| Размер batch движка | Время, с | Записей/с | Отличия адресных полей от базового прогона |
| --- | ---: | ---: | ---: |
| 1 | 0.143 | 7.00 | 0 |
| 8 | 0.535 | 14.96 | 0 |
| 32 | 2.413 | 13.26 | 0 |
| 128 | 10.888 | 11.76 | 0 |
| 1000 | 93.222 | 10.73 | 0 |

Это измерения `Engine.NormalizeBatch`, без HTTP-сериализации. Лимит 5 минут выдержан для этого набора. Проверки HTTP выполнены отдельно. ID, порядок и исходные строки сохранены; предупреждений о недоступности моделей нет.

Извлечение libpostal для 31 строки заняло около 5 мс, GLiNER — 2.42 с. Без GLiNER полный проход 1000 fixture-записей занимает менее секунды и сохраняет адресные поля; это потенциальный выигрыш на текущем наборе, а не универсальный прогноз.

Отдельный полный FP32-прогон обработал 1000 записей за **112.99 с** (8.85 записей/с), без деградации моделей и без отличий адресных полей от своего базового FP32-прогона. Лимит времени выдержан и здесь. Этот вариант медленнее текущего int8 и хуже по качеству на проверенном наборе; менять runtime на FP32 автоматически не следует.

Увеличение HTTP-чанка GLiNER не дало ускорения: 128 строк обработаны за 10.89 с при chunk=8, 10.52 с при chunk=32, 13.38 с при chunk=128. Во всех случаях ответы одинаковы, но пустые. Сейчас размер HTTP-чанка не следует путать с microbatch модели, который остаётся 8; убедительного основания менять 32 по этому однократному замеру нет.

### Рост каталога

Отдельный Go benchmark: 100 адресов, без моделей/КАТО, искусственный каталог, один прогон. Подготовка каталога исключена из времени, snapshot и matching включены.

| Зданий | Время на 100 адресов | Выделено памяти за проход, примерно |
| --- | ---: | ---: |
| 0 | 11.2 мс | 1.16 MB |
| 100 | 88.7 мс | 7.70 MB |
| 1000 | 812.7 мс | 64.45 MB |
| 10 000 | 7.67 с | 642.64 MB |

Это объём аллокаций, не RSS. `reconcile` делает три прохода по зданиям на адрес: города, corroboration улицы/дома, финальные кандидаты. `contains` каждый раз заново токенизирует строку и поля каталога. Сложность растёт примерно как `адреса × здания`; при наполнении каталога это станет существенным расходом даже после оптимизации GLiNER.

## Приоритет изменений

1. **Сначала безопасность и правильные границы компонентов.** Собирать все явные номера домов и конфликтовать при нескольких значениях; выявлять корпус/строение. Разбирать микрорайон вместе с его буквенно-числовым именем и отдельным домом. Добавить обратные маркеры с пробелами и границы токенов. Сильное regex evidence не должно безусловно подавлять структурно согласованный разбор.
2. **Общий слой обработки административных evidence.** Нормализовать городские маркеры и двуязычные пары до голосования независимо от источника. Исключать распознанные spans ориентиров/доставки из поиска города. Ограничивать aliases и иерархию контекстом города/области; сохранять исходное написание улицы.
3. **Пересмотреть роль GLiNER и измерять вклад.** Int8 подавляет выдачу в текущей среде; FP32 возвращает сущности, но ухудшает итоговое качество на этом наборе. Не включать FP32 только ради непустой выдачи. Проверить адресные метки/дообучение, допустимые spans и конфликты с правилами на train/holdout; сравнивать конечные поля после reconciliation. Контролировать долю пустых предсказаний; добавить проверку качества на известных контрольных текстах. После подтверждения качества направлять на вторую модель только строки с недостающими основными полями/конфликтами; критерий должен основываться на evidence, а не просто на текущем confidence. Это осознанное изменение существующего обязательного второго прохода, требующее отдельного внедрения.
4. **Индексировать snapshot каталога.** Предвычислить канонические ключи, tokens, городские aliases и индекс `(street identity, house) → candidates`; затем фильтровать по городу и типу. Для corroboration сначала находить упоминания улиц в индексе. Строить snapshot один раз на revision и атомарно публиковать после успешной записи; не читать overlay многими writer-процессами. Сохранять все кандидаты и отказ при неоднозначности. Не вводить кэш готовых ответов по raw/ID.
5. **Ограничить очередь и локализовать сбои GLiNER.** Сейчас один lock сериализует все запросы; дополнительные HTTP-горутины не ускорят inference. Нужны ограничение ожидающей работы и учёт дедлайна. Ошибка позднего чанка сейчас отбрасывает уже полученные predictions для всего batch: полезнее отдельный результат/ошибка на чанк и предупреждения только для затронутых строк. Проверять cancellation и между Go-этапами: нынешний timeout контекста непосредственно ограничивает HTTP модели, но не все последовательные циклы.
6. **Настраивать batch по метрикам.** Измерять preprocessing/postal/model/reconciliation, длины и число окон, глубину очереди, деградации, unmatched/needs_review, пустые predictions. Изучить группировку модельных окон по длине с обратным восстановлением порядка. Microbatch, число потоков, квантование и допустимую конкурентность подбирать на фиксированном holdout и целевом CPU. Не параллелить native parser в одном процессе: его mutex преднамеренный.

Для публикации реальных координат необходим отдельный проверенный каталог зданий с provenance. Оптимизация разбора не создаст отсутствующее географическое покрытие.

`NORMALIZATION_AUDIT_SKIP_BATCH=true` пропускает дорогие повторные модельные batch-прогоны, оставляя сравнение этапов и быстрый batch без GLiNER. Проверки audit являются измерительными: `PASS` означает успешное выполнение эксперимента, а не отсутствие перечисленных дефектов. Отчёт геокодера содержит явный счётчик `failures`.

`nlp/audit_runtime.py --model PATH --cases PATH --output PATH [--quantize]` запускается в подготовленном Python-окружении, отдельно в FP32 и int8. Он сравнивает выдачу при текущих/русских метках и порогах 0.25/0.10; количество сущностей не считается метрикой качества. Пустые рабочие строки исключаются, добавлены русский и английский контрольные тексты. Для строгого offline-прогона использовать контейнер с `--network none`.
