# Геокодеры и усиление libpostal: исследование 16 октября 2026

Рекомендация: сохранить libpostal, заменить обязательный GLiNER на ограниченный поиск вариантов разбора и проверку по структурным справочникам. Первым внешним по отношению к Go, но локальным offline-кандидатом для эксперимента выбрать Nominatim. До его внедрения расширить покрытие адресных данных и исправить объединение evidence: сейчас правильный результат парсера иногда теряется после regex.

Это исследование и диагностический прототип. GLiNER удалён из текущего пайплайна 16 октября 2026; ниже сохранены исходные предложения и измерения до удаления. Геокодеры не развёрнуты и не прошли сравнительный benchmark на наших данных; ниже отдельно обозначены документированные возможности, локальные измерения и предложения.

## Что дают существующие решения

| Решение | Документированные возможности | Как применить здесь | Ограничения |
| --- | --- | --- | --- |
| **Nominatim** | Free-form и structured search, административный контекст, ограничения страны/территории, детали и языковые варианты названий | Первый кандидат для проверки гипотез «город + улица/микрорайон + дом» по локальному OSM | Нужны импорт и адресные данные; наличие ответа не доказывает точное совпадение здания |
| **Photon** | Многоязычный поиск, typo tolerance, фильтры территории и OSM tags, поиск через OpenSearch | Кандидат для второго поиска улиц с опечатками, если локальные aliases/fuzzy index недостаточны | Дополнительный Java/OpenSearch stack; стандартный импорт построен на Nominatim |
| **Pelias** | Сборка геопоиска из OSM/других источников, libpostal, административные сервисы, exact/interpolated/fallback результаты | Рассмотреть при нескольких крупных источниках адресов и необходимости отдельной геопоисковой платформы | Elasticsearch и несколько сервисов; сложнее нынешнего Go + SQLite. Не даёт автоматически лучшего покрытия Казахстана |
| **2ГИС** | Прямое/обратное геокодирование, здания/административные данные; облачное и On-Premise размещение | Коммерческий кандидат для сравнения регионального покрытия, либо лицензированные данные/закрытый контур | Нужны доступ и подходящие условия; качество покрытия нужных городов надо измерять |
| **Яндекс Геокодер** | Структурный ответ и разные уровни точности совпадения дома | Внешний ориентир качества на разрешённых публичных адресах, если есть доступ | Облачный API не выполняет наш offline runtime; стандартная лицензия не разрешает сохранять/редактировать полученные данные |

Источники: [Nominatim Search](https://nominatim.org/release-docs/latest/api/Search/), [Photon](https://github.com/komoot/photon), [Pelias installation](https://github.com/pelias/documentation/blob/master/pelias_from_scratch.md), [Pelias result quality](https://github.com/pelias/documentation/blob/master/result_quality.md), [2ГИС Geocoder](https://docs.2gis.com/api/search/geocoder/overview), [Яндекс response](https://yandex.com/maps-api/docs/geocoder-api/response.html), [лицензии Яндекса](https://yandex.com/dev/commercial/doc/en/concepts/jsapi-geocoder).

Выбор Nominatim первым — инженерная гипотеза о соответствии нашей задаче, не результат измеренного превосходства над Photon/Pelias. Для эксплуатации нужен собственный экземпляр. [Публичный сервер Nominatim](https://operations.osmfoundation.org/policies/nominatim/) ограничивает частоту максимум одним запросом в секунду и не подходит для нашего обязательного batch/offline-прогона.

В Nominatim есть документированная конвертация подготовленной PostgreSQL-базы в read-only SQLite. Это интересно для автономной поставки, но функция **экспериментальная**, требует Spatialite и Python API; первичный импорт всё равно идёт через PostgreSQL. Это не та же схема SQLite, которую сейчас читает Go. Для первого корректного сравнения разумнее стандартный PostGIS-вариант. [Документация SQLite](https://nominatim.org/release-docs/latest/customize/SQLite/).

Все три открытых геокодера сильно зависят от данных. Если нужного дома нет в OSM, замена поискового движка не создаст точный адрес. Нынешний справочник содержит улицы лишь в части Астаны и не содержит зданий с координатами. Есть [OSM extract Казахстана](https://download.geofabrik.de/asia/kazakhstan.html), но наличие extract не означает достаточную полноту адресных тегов. Её нужно отдельно посчитать по городам.

## Усиления libpostal

### Несколько вариантов входа вместо одного разрушительного преобразования

Варианты для сложной строки:

1. Неизменённая рабочая строка.
2. Разделение слитных имени и номера / номера и маркера: `Назарбаева8` → `Назарбаева 8`, `11дом` → `11 дом`.
3. Адресная часть после выделения spans квартиры, подъезда, этажа и ориентира; исходные детали сохраняются отдельно.
4. Альтернативная трактовка обратных маркеров, если `5 подъезд 239 кв` допускает разные границы.
5. Русская/казахская половины двуязычного города как отдельные гипотезы при подтверждённой эквивалентности.

Сохранять исходный вариант обязательно. Например, удаление числа перед `кв` без анализа контекста может удалить дом из `9 кв 1`. Нельзя разделять числовые идентичности без оглядки на роль: `12а`, `55/6`, номер микрорайона и номер корпуса должны сохраняться. Нужна карта offsets обратно в raw, чтобы возвращать исходное написание улицы.

### Проверено на настоящем native parser

Добавлен `scripts/probe-libpostal.py`. Он запускает пять вариантов строки × три настройки языка (`auto`, `ru`, `kk`), всегда с `country=kz`. Никакие справочники или ответы геокодеров не подставляются. Считается, присутствует ли правильное непустое значение улицы/дома среди соответствующих компонентов libpostal после удаления маркера типа улицы. Учитываются дроби и литеры.

| Набор / обработка | Найденные правильные значения улицы/дома |
| --- | ---: |
| 30 синтетических адресов: исходный вариант | 44 / 53 |
| Те же адреса: разделены слитные токены | 46 / 53 |
| Те же адреса: адресная часть, обратные маркеры обрабатываются первыми | 49 / 53 |
| Те же адреса: адресная часть, прямые маркеры обрабатываются первыми | 52 / 53 |
| Объединение кандидатов всех вариантов | 52 / 53 |
| 58 публичных KZ-адресов Senzing: исходный и каждый преобразованный вариант | 113 / 116 |

Для синтетического набора 450 вызовов/вариантов заняли около **19 мс**, для публичного KZ-набора 870 — около **46 мс**, без загрузки модели. Это время диагностики, не end-to-end API latency. `auto`, `ru`, `kk` дали одинаковые результаты на каждом наборе. Само принудительное назначение языка здесь пользы не показало.

**Это покрытие кандидатов, а не точность готового pipeline.** Не проверены лишние значения/null-safety и автоматический выбор варианта; несколько компонентов одного типа могут содержать одновременно правильный и неправильный ответ. Синтетические случаи использовались при разработке преобразований, поэтому результат нельзя считать holdout. Набор Senzing тоже не является независимым от обучения libpostal. Проверялись лишь улица/дом, не все одиннадцать полей. Неразрешённый синтетический случай — название микрорайона `Нурсити 2`: номер дома находится, полное имя территории по-прежнему теряется.

Тем не менее эксперимент показывает, куда полезно потратить бюджет: повторный native parse дешёвый, а изменение границ строки даёт дополнительные правильные кандидаты. Сначала надо построить безопасный selector, а не объявлять 52/53 точностью приложения.

Публичные KZ-случаи получены из [Senzing test_data.csv](https://github.com/Senzing/libpostal-data/blob/main/files/tests/v1.2.0/test_data.csv), отфильтрованы по `country_code=kz`. Загруженные файлы и результаты находятся только в `.artifacts/geocoder-research/`.

### Expansions и словари

В текущем адаптере используется только `libpostal_parse_address`. В библиотеке также есть `libpostal_expand_address` для построения поисковых вариантов, настройки разбиения букв/чисел и языковые словари. Их следует применять к ключам поиска улиц/названий, а не к возвращаемым значениям или числовой идентичности здания. [API header](https://github.com/openvenues/libpostal/blob/master/src/libpostal.h), [формат словарей](https://github.com/openvenues/libpostal/blob/master/resources/dictionaries/README.md).

Локально проверено с явным `ru` и подготовленными base assets:

- `ул. Курильская` даёт вариант `улица курильская` и транслитерации.
- `Назарбаева8` даёт варианты со слитным и раздельным номером.
- `мкр. Аксай 3а` даёт несколько вариантов, включая раздельную литеру.
- **`55/6` превращается в `55 6`**, даже при отключённом изменении числовых дефисов. Поэтому expand нельзя напрямую применять к номеру дома.
- Для `Тұран даңғылы` при `ru` получены частично транслитерированные варианты; полноценную казахскую нормализацию это не подтверждает.

В просмотренном upstream-каталоге ресурсов есть `ru`, но нет отдельного `kk`. Это пробел словарных ресурсов, а не доказательство отсутствия казахских примеров в обучении. Первое усиление для нас — собственные проверенные ru/kk aliases и маркеры в immutable reference. Вклад в upstream-словарь тоже возможен, но требует подготовки новых assets и проверки регрессий; редактирование текстового словаря не равно мгновенному дообучению parser.

### Альтернативная модель Senzing

Можно A/B проверить Senzing parser model вместо default. Новые веса надо подготовить заранее и запускать отдельно, поскольку libpostal имеет глобальное состояние. Но обещать улучшение Казахстана по общей цифре качества нельзя: в опубликованном сравнении Senzing v1.1 → v1.2 на 58 KZ-случаях число ошибок выросло с 0 до 1. Это сравнение двух Senzing-версий, **не** сравнение с нашей default-моделью. Саму Senzing-модель здесь не скачивали и не запускали. [Модель и версии](https://github.com/Senzing/libpostal-data), [разбивка по странам](https://github.com/Senzing/libpostal-data/blob/main/files/stats/v1.2.0/Parsing_comparison_v1_2_0.md).

Переобучение libpostal — более дорогая подготовительная работа, не первый шаг: сейчас есть дешёвые структурные ошибки вокруг уже работающего parser. Оценивать новые веса надо на размеченных местных адресах, с отдельными группами микрорайонов, двуязычности и слитных маркеров.

## Предлагаемая архитектура

```text
raw + неизменяемые offsets
  → локальная грамматика маркеров, детали доставки, конфликтующие числа
  → libpostal на исходном тексте
  → для сложных случаев: до 4 дополнительных вариантов → libpostal
  → кандидаты полей со spans, ролями и происхождением
  → проверка по иерархии КАТО и ru/kk aliases
  → exact lookup в индексированном каталоге зданий
  → если остались кандидаты: ограниченный локальный geocoder lookup
  → проверка города, улицы, точного дома/корпуса, отрыв от второго кандидата
  → отдельная уверенность разбора и выбора здания
```

Повторные разборы одного libpostal не считаются независимыми голосами. Nominatim, Photon и Pelias, построенные на одном OSM, также не дают трёх независимых подтверждений. Выбирать нужно согласованный структурный разбор, а не наиболее частое слово среди зависимых источников.

Для микрорайона `Аксай 3а, 59` проверяются два структурных кандидата. Кандидат с территорией `Аксай 3а` и домом `59` получает преимущество при подтверждении справочником; при отсутствии покрытия сохраняется неопределённость. Нельзя предпочитать неправильный дом только потому, что его номер случайно нашёлся в каталоге. Явные конфликтующие дома/корпуса остаются препятствием для уверенного геокодирования.

Fuzzy matching использовать для названий в пределах установленного города и разумных кандидатов, не для произвольной замены номера дома. Ошибки и падежи в `street_name` сохраняются из raw; каноническое имя служит поиску и сопоставлению. Результат geocoder уровня улицы/района может подтвердить компонент, но не становится координатами здания. У Pelias `point` не исключает интерполяцию; нужно отдельно проверять `match_type`. У Яндекса `number`, `near`, `range` отличаются от `exact` и не должны приравниваться к точному корпусу.

Данные должны оставаться раздельными:

- КАТО/улицы/aliases — существующий immutable reference.
- Подготовленный адресный индекс и, если появятся проверенные координаты, immutable building facts с происхождением, покрытием и уровнем точности. Это новый слой, не самовольное добавление координат в текущую KATO-схему.
- Подтверждения пользователей — writable overlay с прежними revision/atomic-write гарантиями.

Импорт OSM не делает каждый адрес подтверждённым человеком. Источник и характер координат — адресная точка, представитель геометрии здания, интерполяция — должны сохраняться. Apartment/entrance/floor/landmark не становятся дефолтами здания. Кэша готовых ответов по raw/ID нет.

## На что потратить время

Предельный бюджет 300 с на 1000 записей соответствует 300 мс/строку в среднем при последовательном исполнении, включая остальные этапы. Нынешний замер без GLiNER — 0.27 с/1000 на маленьком каталоге; нельзя считать это гарантией на наполненном справочнике. До добавления дорогого lookup необходимо убрать три линейных сканирования каталога для каждой строки.

Предлагаемый начальный предел: до пяти parser-вариантов для сложной строки, до двух/трёх geocoder-запросов и до пяти результатов на запрос, с дедлайном на batch и ограниченной очередью. Это проектные ограничения для проверки, не измеренные оптимальные значения. Дорогой путь нужен только строкам с неполными или конфликтующими структурными полями.

Нужно измерять отдельно parser time, candidate recall, качество selector, precision координат, coverage и tail latency. Цель первого рабочего варианта — уложиться в 120 с/1000 на целевом CPU, сохраняя запас до пяти минут; это целевой бюджет, не обещание производительности Nominatim.

## Следующие проверяемые шаги

1. Отключить GLiNER штатным изменением конфигурации/кода, убрать только его outage-warning/штраф. Сохранить baseline для сравнения.
2. Исправить grammar и reconciliation; реализовать bounded parser hypotheses со spans. Проверить все 11 полей и отсутствие ложных координат, а не только candidate recall.
3. Расширить источник улиц/адресных точек за пределы части Астаны; посчитать реальные `addr:housenumber + addr:street/addr:place`, полноту ru/kk names, корпуса и дубли по городам. Проверить происхождение координат до публикации их как building facts.
4. Собрать отдельный локальный Nominatim на том же подготовленном extract. Сравнить исходный запрос, структурный запрос после первого parse и ограниченный поиск нескольких гипотез. Отдельно учитывать точный дом, street fallback и отсутствие объекта в данных.
5. Проверить Photon только на группе опечаток, где aliases и обычный поиск не справились. Pelias оставить как вариант при доказанной потребности в объединении нескольких источников.
6. A/B default/Senzing и словарных улучшений на фиксированном наборе, затем на holdout из реального потока. Делить набор по зданиям/семействам адресов, чтобы разные квартиры одного дома не попадали одновременно в настройку и оценку.

Критерии принятия: больше полностью правильных записей и основных полей; не увеличивается число ложных полей и ложных геокодов; сохраняются raw/ID/порядок; корректно различаются дробь/литера/корпус; batch 1000 проходит за пять минут при отключённой сети. Сравнение геокодеров проводить на одном snapshot данных, иначе улучшение покрытия смешается с качеством поиска.

## Повторение локального эксперимента

```bash
python3 scripts/probe-libpostal.py \
  --library /absolute/path/to/platform-matched/libpostal.so \
  --data /absolute/path/to/prepared/libpostal/data \
  --cases backend/internal/normalize/testdata/audit.synthetic.json \
  --output .artifacts/geocoder-research/libpostal-hypotheses.json \
  --expansions
```

Нужны native library и соответствующий ей header ABI; в ctypes описаны структуры подготовленной версии. Новых Python-зависимостей нет. Инструмент использует только локальные assets, ничего не загружает и не меняет рабочие каталоги. Проверены реальный запуск на обоих наборах и `python3 -m py_compile scripts/probe-libpostal.py`.
