# Архитектура и совместимость

[Документация](README.md)

## Один проект, три независимых приложения

Jana Locate — основной публичный репозиторий и место для issues, изменений и документации.

```text
Свой сервис ── HTTP ────────────────────► Go API
Браузер ────── HTTP ────────────────────► Go API
CLI ────────── HTTP ────────────────────► Go API
 │                                         │
 ├─ файлы / PostgreSQL                     ├─ libpostal + правила
 ├─ локальный SQLite-журнал                 ├─ immutable КАТО/OSM
 └─ встроенный интерфейс проверки           └─ согласование полей и неоднозначностей
```

`backend/` владеет нормализацией, справочником, заданиями и HTTP-контрактом. `frontend/` — независимая SPA: собирается только из своего каталога, использует внешний URL API, не читает Go-исходники и не вызывает API при prerender. В production работают статические файлы и Nginx, без Node-сервера.

`cli/` — независимый Go-модуль. Он получает согласованный снимок PostgreSQL или читает файл, хранит прогресс и исправления в SQLite, вызывает нормализатор и по явному подтверждению публикует результаты. Исходная таблица не изменяется. В бинарник включён проверенный build общего frontend; Node в runtime не нужен.

## Контракты

- `backend/api/openapi.json` — источник истины нормализации.
- `frontend/src/api/openapi.json` — принятый frontend снимок.
- `cli/api/normalization.openapi.json` — принятый CLI снимок.
- `cli/api/openapi.json` — отдельный локальный API оркестрации.
- `make generate` обновляет DTO и снимки; `make check` проверяет соответствие.

Исходники приложений не связываются общим workspace. Их граница — HTTP и явно принятые контракты.

## Нормализация

Native libpostal, правила и неизменяемые КАТО/OSM дают свидетельства для согласования в Go. Явные конфликты и совместимые омонимы сохраняются. Язык ввода не выбирает страну назначения: география — Казахстан.

Геокодирование и чтение building overlay исключены из нормализации. `coordinates`, `catalog_id`, `catalog_revision` у новых результатов равны `null`. Legacy-каталог доступен отдельно; его наличие не улучшает confidence и не разрешает неоднозначности.

Справочник содержит административные сущности, улицы, адресные свидетельства и районные отношения без координат зданий. Источники и полнота зафиксированы в manifest. Рабочие задания и legacy-подтверждения хранятся отдельно от immutable-данных.

## Публичные имена и версии

Историческое имя backend-модуля `github.com/lukivan8/jana-address` сохранено; переименование Go-пакетов не требуется для HTTP-интеграции. Самостоятельная старая публикация Jana Address не является актуальным источником кода. Новый код и документация находятся здесь.

До появления версионированных артефактов фиксируйте commit Jana Locate. Версия `info.version` в OpenAPI описывает API и не заменяет версию исходников/справочников. На изменения `/v1` сначала меняется спецификация, затем генерируются DTO. Несовместимое изменение требует отдельного решения о версии API.

Старые сохранённые результаты не пересчитываются автоматически. Версии справочника и локального CLI API независимы; их совместимость проверяется принятыми снимками и тестами.

## Хранение и сеть

Один API-процесс владеет одним записываемым overlay и хранилищем заданий. Локальный SQLite CLI — журнал выполнения и правок, а не кеш ответов для будущих адресов. Полные адреса, входные ID и детали доставки не становятся ключами или значениями здания по умолчанию.

Runtime использует подготовленные локальные модели и справочники. Онлайн-геокодер и загрузка весов во время работы не требуются. Публичная сеть нужна только для подготовки и, если настроено владельцем, доступа пользователей к приложению.
