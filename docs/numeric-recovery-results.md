# Baseline + компактный числовой слой — 18 октября 2026

Выбран кандидат `native-numeric-crf-v1`: действующий native пайплайн
(libpostal + существующая обвязка + справочники) остаётся основой. Небольшой CRF
дополняет только пустые числовые поля. Он не заменяет непустые значения, не меняет
географические кандидаты, предупреждения, status или расчёт confidence baseline.
При недоступности модели возвращается исходный native результат. Публичный сайт `jana.linker.kz` использует этот кандидат с 18 октября 2026.
Автодеплой остаётся остановленным; порядок отката — в [инструкции выпуска](numeric-deployment.md).

## Что проверено

4608 строк прошли фактический HTTP API изолированного кандидата: прежние 4488 и
120 новых диагностических строк. Все поля/статусы совпали с офлайн-оценкой слоя.
671 различие confidence — округление порядка 1e-16 между отдельными native
запусками; ещё 86 различий — порядок предупреждений. Состав предупреждений,
отображаемые проценты и решения не изменились. Сырые различия сохранены.

На 4544 строках есть числовая разметка, включая отрицательные поля; 64 строки
без такой разметки проверены на паритет, но не засчитаны в качество. Обнаружено
1145 исправлений отдельных числовых полей, 0 новых ошибок относительно baseline.
Это сравнение с синтетической LLM-разметкой, не гарантия для произвольного ввода.
2716 исходных строк участвовали в обучении/диагностике, поэтому их результат
не является независимой оценкой переноса.

Все четыре числовых поля одновременно совпали с разметкой (отсутствие также
проверяется):

| Набор | Строк | Native baseline | Native + CRF |
|---|---:|---:|---:|
| Контроль 2 | 204 | 101 | 123 |
| Числовой контраст | 144 | 24 | 84 |
| Числовые сложные случаи | 216 | 60 | 93 |
| Ориентиры/инструкции | 384 | 64 | 256 |
| Исходная диагностика, не holdout | 2716 | 1760 | 2232 |

Отдельный набор создан после фиксации компактной политики: 32 синтетических
примера, четыре семейства — смешанные RU/KK, RU/UZ, RU/EN компоненты и числовые
отвлекающие элементы в ориентире. Одновременно проверены city, street_name,
house, apartment, entrance, floor: baseline 0/32, кандидат 16/32, новых ошибок
по полям нет. Это 4 шаблонных семейства, не 32 независимых реальных адреса;
название улицы синтетическое, существование здания не подтверждается.

Полное совпадение адреса нельзя подменять совпадением числовых полей. На прежних
наборах сохраняются ошибки улиц, населённых пунктов и ориентиров. Диагностический
скалярный счёт по всем размеченным полям вырос лишь с 536 до 538/2685; отсутствующие
географические метки в нём не оцениваются. Этот показатель не означает, что лишь
две числовые поправки полезны, но показывает оставшийся предел полного разбора.
Новый числовой слой не решает все задачи нормализации и не объявлен насыщением.

## Скорость и память

Свежий изолированный API: первые 1000 строк 3.250 с, следующие 1000 — 2.995 с.
Лимит API 2 CPU / 3 GiB; числовой сервис 1 CPU / 128 MiB. Замер включает native
разбор, справочники, HTTP к числовому сервису, слияние и сериализацию результата.
Это локальный HTTP через Docker exec, не публичный Cloudflare-маршрут.

Пиковая cgroup-память API — 2516508672 байта (2.344 GiB), дополнительного сервиса —
49172480 байт (46.9 MiB); пики не обязательно одновременны. Модель — 215988 байт.
XLM-R и вторая копия libpostal этому варианту не нужны. Память исходного native
libpostal этим изменением не уменьшена.

## Почему выбран именно этот вариант

Вначале проверялась правка numeric-разбора поверх v7. Она исправила `9 кв1` и
`3подъезд 2этаж`, прошла 1000 через HTTP за 87.2 с, но весь v7 всё ещё проигрывал
baseline в отдельных случаях. Вариант с согласованием XLM-R и CRF также дал
дополнения без обнаруженных регрессий, однако требовал тяжёлый encoder.
Для текущей цели оставлен компактный вариант; альтернативы сохранены только в
игнорируемой лаборатории и в экспериментальных Docker-образах.

CRF использует слова, Unicode-токены, границы склейки и локальный контекст.
Цифровые значения маскируются в признаках. Нет сопоставления всей строки, ID,
списков готовых адресных ответов или regex-исключений для приведённых примеров.
Обучение: 3540 допущенных ранее строк + 880 синтетических. Порог 0.99 фиксирован
для компактного дополнения. Это posterior тега, а не вероятность правильности
адреса. Исходная уверенность сохраняется, её область действия записана в
`normalization_details.numeric_supplement.confidence_scope`.

## Ограничения и подключение

Слой намеренно не исправляет непустое ошибочное поле baseline и не снимает
неоднозначность. Это следующий отдельный класс работы: разрешённые замены должны
показать выигрыш на полноценном разборе, сохраняя прежние корректные случаи.
Статус автоматически не повышается из needs_review в matched.

В native backend задаётся `NUMERIC_SUPPLEMENT_URL`; режим несовместим с
`CONTEXTUAL_NORMALIZER_URL`. Конфигурация для изолированного запуска —
`compose.numeric.yaml`. Runtime числового сервиса изолирован внутренней сетью.
Перед сборкой подготовить `jana-numeric-deps:0.9.12` через
`backend/contextual/Dockerfile.numeric-deps` и модель по хешу из README;
`Dockerfile.numeric` собирается офлайн. Ни веса, ни пакеты при старте не скачиваются.

Проверки: backend go test -race ./..., go vet ./..., тесты с native libpostal при
Docker-сборке, make smoke, Python-тесты признаков, живой HTTP-паритет 4608 строк,
перенос на 32 новых примера, отказ дополнительного сервиса с сохранением native
ответа. Контракт API и фронтенд в этой итерации не менялись.

Артефакты: `.artifacts/normalization-lab/goal/numeric-recovery-v4/` — manifest,
зафиксированная модель, исходные/контрольные наборы, компактные и отклонённые
варианты, исходные HTTP-ответы, сравнения, времена и логи. Ни один из этих наборов
не читается во время работы сервиса.
