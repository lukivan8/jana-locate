# Дополнительные синтетические примеры районов

Отдельный набор **240** LLM-созданных и размеченных строк, расширяющий покрытие
районов. Исходные 2000 строк и их разметка сохранены без изменений; контрольные
суммы проверяются сборщиком. Это материал для проверки покрытия и будущего
обучения/оценки, не измеренная точность текущего нормализатора.

Итог: **208** строк с явно размеченным районом, **32** отрицательных примера,
**36** строк со специально заданными конфликтами/неоднозначностью. Языки:
62 RU, 58 KZ, 60 UZ, 34 русских транслитерации и 26 смешанных; дополнительные
теги отражают пересекающиеся признаки. Упомянуты 42 районные сущности справочника
(включая альтернативы и контекст отрицательных примеров).

## Содержимое

- `inputs.json` — массив `{id, raw_address}`, пригодный для загрузки как отдельный
  пакет (240 записей).
- `inputs.jsonl` — тот же ввод построчно.
- `annotations.jsonl` — выбранные фрагменты, позиции, поля и сценарные признаки.
- `coverage-report.json` — фактические количества языков, признаков, районных
  фрагментов, отрицательных примеров и диагностик; результаты проверки структуры.
- `shards/*.cases.jsonl` — 240 явных LLM-решений трёх исполнителей.
- `reference-context.json` — контекст из 171 районной/административной сущности
  локального КАТО с aliases, родителями и примерами населённых пунктов.
- `source-manifest.json` — происхождение, контрольные суммы, область применения.
- `reference-enrichment-fixtures.json` — 16 отдельных синтетических сценариев
  будущего обогащения района по справочнику. Это описание ожидаемого поведения,
  не результаты запуска нормализатора и не действующие географические связи.

## Покрытие текстового извлечения

Городские районы Алматы, Шымкента и Астаны, областные сельские районы,
повторяющиеся названия в разных регионах. Примеры на русском, казахском,
узбекском, с транслитерацией, смешением письменностей, опечатками, сокращениями,
слитными маркерами, перестановкой компонентов и отсутствием пунктуации.

Отрицательные примеры содержат название района только в названии улицы,
заведения/ориентира или инструкции доставки, либо не содержат района вообще.
В них `district` отсутствует в разметке. Конфликтные примеры сохраняют все явно
написанные районы, несовместимые административные контексты и омонимы.
У разных языковых вариантов одной сущности может быть несколько district-spans
без конфликта идентичности; это также отражено в примерах.

Шесть районов Астаны и район Тұран Шымкента в текущем снимке имеют исходный
тип `admin`, но роль района в тексте всё равно размечена как `district`.
Набор не меняет исходный КАТО и не считает все сущности `admin` районами.

Названия административных единиц взяты из локального снимка КАТО;
улицы, дома, квартиры и детали доставки синтетические. Набор **не утверждает**
существование этих адресов или принадлежность реальных улиц указанным районам.
Узбекские фразы и транслитерации созданы LLM и не проверены носителями языка.

## Метки и неоднозначность

Основной формат spans совместим с соседним набором `address-anomalies-v1`:
`start` включительно, `end` исключительно, в Unicode code points исходной строки.
Фрагменты привязаны к raw и не пересекаются. Числовые маркеры не входят в номер;
явная фраза района обычно включает район/ауданы/tumani.

`family_id` объединяет четыре авторских варианта; всего 60 семейств. Все варианты
одного семейства должны оставаться в одной части train/validation/test.
Если несколько семейств используют общую исходную географическую/адресную
основу, их также следует объединить перед разделением, чтобы исключить утечку.
Разбиение на независимый тест пока не выполнено.

`reference_ids` — справочный контекст, а не обязательные единственные ответы.
`expected_input_issues` отмечает специально заложенные свойства сценария;
пустой массив не доказывает географическую однозначность. Он не является
исчерпывающей разметкой всех runtime diagnostics. Весь набор предназначен для
извлечения текста, а не обучения подавлению неоднозначности по выбору LLM.

Отсутствующий в тексте район не получает span даже при возможности дополнить
его по справочнику. Извлечение фрагмента, идентификация района и обогащение
адреса — отдельные задачи. Подсвеченная неоднозначность является допустимым
результатом нормализатора; частота города в синтетике не исключает село-омоним.

## Сценарии обогащения по адресу

16 спецификационных сценариев используют только фиктивные сущности с префиксом
`fixture:` и явно синтетические предварительно вычисленные отношения:

- улица целиком в одном районе либо пересекает два;
- разные дома той же улицы находятся в разных районах;
- неизвестный дом, дом на границе и противоречащие адресные источники;
- явный район конфликтует со справочным;
- неполная выборка домов и отсутствующее покрытие;
- одноимённая улица другого города и неоднозначность город/село;
- район однозначного села из иерархии;
- дома `10` и `10/1` с разными свидетельствами;
- сохранение явно извлечённого района при отсутствии справочного подтверждения.

Сборщик проверяет лишь целостность ссылок этих сценариев. Будущую реализацию
нужно отдельно проверить по ним. В действующий справочник они не загружаются.
План реализации: `backend/docs/district-reference-plan.md`.

## Воспроизведение

Из корня репозитория:

```sh
python3 scripts/assemble-district-annotations.py
```

Скрипт применяет буквальные авторские выборки, вычисляет spans и проверяет
ID, порядок, уникальность строк, семейства, справочные ID, отрицательные случаи
и сохранность исходного набора. Семантический парсер и нормализатор не вызываются.
Runtime и фронтенд не менялись; исходная страница 2000 примеров остаётся прежней.
